# Basic’s Advanced Timer: engineering notes

Notes for contributors and coding assistants. The application is a C# Avalonia desktop app on .NET 8, always on top, for tracking time against client accounts and preparing timesheets. It must run without installs or administrator rights. The earlier PowerShell/WinForms app (v2.32) was removed from the tree and lives in Git history.

## Branches and releases

`main` is the Store release, `experimental` is everyday testing and `alpha` is for risky prototypes. Work on `experimental` or a `feature/...` branch from it, promote alpha to experimental and experimental to main by pull request, and never push straight to `main`. Builds show their channel beside the version, and only non-Store builds offer the sample-data demo. The updater serves experimental and alpha only, each with its own data, versions and backups. See `BRANCHES.md`.

## Behaviour to preserve

- **Working time and allocation.** Reports show Working time as Allocated (time on accounts) plus Unallocated (working clock time not on any account, never below zero), with Breaks separate and not counted. The running entry's elapsed time is included (`TrackingEngine.ActiveElapsedOn`). Budget figures for an earlier week use that week's own period (`TimerModel.BudgetReference`, `BudgetUsedAt`, `BudgetPeriodNameAt`, the Thursday rule), never "this month". Hiding an account (In tracker) only removes it from the tracker list. Its time stays in `ReviewAccounts` and every report. Scroll views that end above fixed controls use `Ui.WithMoreBelow`, which draws a one pixel line in the theme's Line colour along the edge with more content past it, below and, once scrolled, above (a fade or shadow looked muddy on light themes).
- **Colour roles.** Green (`Live`) means tracking only, the accent means selection, focus and the main action (a blue in Light and Dark, kept clear of red, green and orange), amber means a break, `BudgetWarning` means a budget at 80 per cent and red (`Overtime`) means overtime or a spent budget. A budget bar with room left is neutral (`Muted`), the setup's current step dot is the accent, and the idle pill dot is `Idle`.
- **Duration format.** Every duration reads as HH:MM (`TimerModel.Format`, `FormatShort` and `FormatCompact` all give 01:30), and as decimal hours when that is chosen. Do not add a new way of writing one.
- **Credited totals.** Entries hold credited durations. Totals come from credited seconds, never from clock spans. Positioning credit never adds hours; "Add time" does.
- **Day clock.** The main clock is working plus overtime time, excluding Lunch, breaks and away. Stopping or switching an account does not reset it. Scheduled starts are automatic. A day off counts only tracked time. `SetShifts` drops manual starts the new hours make unnecessary. `ResumeAfterBreak` is stored with the running row. `BreakAccount.Name = "Break"` is reserved.
- **Exact decimal hours.** Exports apportion hundredths of an hour by largest remainder, first across account/day totals and then within each bucket, so every sum is exact. Running totals are provisional until saved.
- **Gaps.** Selected gaps are validated against the unrounded current gap before being moved to whole seconds, because durations use hundredths of a minute.
- **Switching accounts.** A block's length is kept to hundredths of a minute and its start to the second, so `TrackingEngine.ToggleAccount` starts the new block at the whole second after the old one's stored end when needed, and consecutive blocks never overlap. The timeline also treats blocks within two seconds as meeting, so older overlaps do not split the day into lanes. After a quick slip from one account to another and back (a block of three minutes or less, switched back within three minutes, `TrackingEngine.ContinuableBlocks`), `ContinuePrevious` drops the short block and reopens the earlier one so it carries on as one, with the slip's time. It is offered in the floating message (`MessageBar`, its `ContinuePrevious` button) for a few minutes, and not for blocks in a group. Making it automatic with an Undo (brief item 57) needs the engine to undo a continue, so the offer stays for now. Pressing play on an account whose block the time now falls inside (one added or pasted ahead of time) carries that block on instead of starting a second one on top of it (`TrackingEngine.FutureBlockOf`, `ContinuedBlock`): it is reopened from its own start, stopping ends it where the recording stops, and it is skipped for a block in a group or one that would overlap other recorded time. A break is carried on the same way, so starting a break inside a break block already there reopens it.
- **Selecting and editing timeline blocks.** A plain click selects just that block (`TimerModel.SelectBlock`), and clicking the only selected block again clears the selection; Shift-click adds a block to the selection or takes it out (that is how two blocks are picked to merge). There is no double-click to edit, which could not be told apart from two clicks. A selected block is edited in the Selected block card under the timeline (`SelectedBlockCard`, whose header is a grid with one stretching row at a fixed height, so its title stays where it is whether none, one or several blocks are selected); there is no Edit button and no Enter shortcut. Right-click menus on a block carry the other actions. Double-clicking empty space still adds time. The block being recorded is not selectable (a click says it is still recording).
- **Dragging to a neighbour.** A block's end is kept to the whole second and its length to hundredths of a minute, so `TimelineGestures` snaps an edge to the neighbour's start with `LastDeltaBefore`, which steps back a second at a time until the saved block really ends no later than it. This matters most for the block being recorded, whose start has a fraction of a second.
- **Undo.** Edits are stored as splices plus hashes in `edits` and `edit_changes`, so history stays small and survives restarts.

## Storage

`TimerDatabase` holds accounts, entries, groups, away, day_starts, running, edits, edit_changes and meta. It takes an exclusive lock, uses WAL and `user_version`, and makes daily backups. The schema is format 2 (a budget can be per day), and `TimerDatabase.Upgrades` holds the numbered steps that take an older file forward after a copy is saved; a step that rebuilds a table runs with foreign keys off and is checked with `foreign_key_check` before it is kept, and an older build refuses a newer file. Dispose every `SqliteCommand` or Windows keeps the file locked, which fails tests on CI. `TimerStore` rewrites `entries` when a snapshot changes. Notes, groups and `accountsSeeded` are blobs in `meta`. The settings JSON preserves unknown sections and is swapped in atomically with a `.bak`. Sessions checkpoint every 15 seconds and recovery stops at the last checkpoint. `TimerStore` refuses a folder holding the old `AccountTimer2.ps1` or launcher, and the old CSV files are deliberately never imported. Never auto-open another app's data folder. Never commit `migration-data`, `timer.db`, settings JSON or logs (`.gitignore` excludes them).

## Themes

Each theme is a `ThemeDefinition` (name, Light or Dark base, colour tokens, block style) and an Avalonia `ThemeVariant`. `ThemeTokens.Names` lists the tokens (Surface, Panel, Ink, Muted, Line, Hover, Selected, Live, Idle, Overtime, BudgetWarning, Break, Finish, Start, Accent, AccentInk, Clock, PillSurface, PillInk, PillBreak, PillOvertime, ShadowColor). `ThemeEngine.Register` writes brushes into `Application.Resources.ThemeDictionaries` in place so open windows repaint. Light and Dark register in `App.Initialize`. The pill (`PillWindow`, in `PillWindow.cs`) is a small vertical card, 72 by 316 with a 36 pixel corner, with the room around it for its shadow or glow (`Ui.ShadowMargin`). From the top it has a pair of lights (the state light, 6 by 14, and the reminder light, which is always there: a quiet grey when nothing is waiting, and blue with a ring that swells from it and fades (`Ui.PulseRing`: seven pixels over 1.8 seconds, as the mock draws it, and still when less motion is asked for) while `TimerModel.ReminderDue`, which is true while a reminder has passed and its note is not ticked off, `NotesModel.AttentionCount`), the day clock stacked as hours, minutes and smaller seconds (`StackedClock`; the tile is the `PillDashboard` button and opens the dashboard), the primary control (`PillPrimaryTile`), the break control (`PillBreak`, a `BreakButton`) and, at the foot, the Accounts button (`PillAccounts`, three short bars in account colours). The three are one shape and size, `StatusFace.TileSize` (44) with `TileRadius` 14, centred with 14 pixels either side and 10 between them, and the card is tall enough (`PillHeight`, 316) to leave the same room under the Accounts button, so no tile or its focus ring crowds the card's edge. Every control is a soft tint of its own colour (`SoftTint`): the primary control green, or red in overtime (the Live or Overtime token at about 20 per cent over the card, initials or symbol in the colour itself), the break the theme's break orange (a soft tile with an orange cup, solid orange with a lit cup, white where it reads on the orange and a dark brown where it does not, plus a soft ring and steam only while a break is on), the Accounts button a quiet wash that turns blue under the pointer and while the drawer is open; each deepens a step under the pointer, and each takes a blue keyboard focus ring (`SoftTint.FocusRing`, shown for keyboard focus only, never after a mouse click). The whole column (lights, clock, primary control, break and Accounts button) is `StatusFace`, shared with the rail so the two tops are identical, and starts `PillWindow.TopInset` below the card's edge on both. The primary control carries the running account's initials (`PillWindow.Initials`, first letters of up to two words), gives way to a play or pause symbol at rest, deepens its tint a little under the pointer (it never grows, which the button's edges would clip), and pauses or resumes; with nothing chosen it opens the account list. On a break it stays green and keeps the account's initials, because the orange break control beside it already says so. The state (Break outranks Overtime outranks Live, else Idle) is the light, the primary control's tint (idle uses the Live colour), a 1.5 pixel ring (70 per cent opaque; the card's edge is `PillWindow.EdgeThickness`, 1.5, in every state and only its colour changes, because a thicker edge only while something happened moved the contents by half a pixel, which showed as a jump, and the column starts that much nearer the top so the lights still sit `TopInset` from the edge) and a soft halo round the card (`Ui.SetPillShadow`, drawn as the mock draws it: a glow of a 12 pixel CSS blur at 16 per cent, 22 on a dark theme, and at rest a shadow dropped 6 pixels with an 18 pixel blur at 10 per cent warm black, 40 per cent black on a dark theme; Avalonia's blur spreads about a third less than a CSS blur of the same number, so `Ui.CssBlur` converts, and a pixel comparison against a Chromium render of the mock's CSS is how it was checked; the ring and glow take the mock's bright mint, amber and coral on a Light theme (`Ui.PillStateColour`, since the theme's own state colours are deeper there and read about one and a half times as strong) and the theme's own state colours on a dark one; the dashboard keeps the card shadow of `Ui.SetShadow`; the pill keeps its shape, ring and glow while the account drawer is open; see the drawer below), the tooltips and the accessible names, so colour never carries it alone. On a dark theme the pill, its drawer and the square behind it wear the rail's card colour (the `PillBody` resource, which `ThemeEngine.Write` writes as Panel on Dark and Surface on Light), so a pill that opens into the rail changes no shade. The card keeps the normal theme in every state (the old per-state pill colours and the three layouts, Full, Compact and Minimal, with `PillLayouts` and the `pillstyle=` line, are gone; `ThemeDerivation.Variant` still exists in the shared package and is unused by the pill). Nothing opens on hover. The Accounts button slides the account drawer out from behind the pill (`PillDrawer`, an Avalonia `Popup` that starts `PillWindow.Behind` (3) pixels under the card's right edge, so no gap shows between the two windows at a fractional screen scale: the same surface, 251 wide and as tall as the pill, square on the pill side and rounded 36 on the far side, with its ring on the top, bottom and far side only, and cut away where the pill's capsule is, `BehindPill`, a `CombinedGeometry` exclude on `PillDrawerHolder`, so the pill's own ring and glow show on top; the pill keeps its round corners, and a square of the drawer's surface (`PillDrawerFiller`, 36 wide, drawn in the pill's own window behind the card while the drawer is open, with its ring top and bottom) fills the corners the capsule cuts away, so the drawer reads as tucked behind the pill; it is in the pill's window so the drawer's window never lies over the pill's controls; the drawer eases out over 420 ms (`PillWindow.SlideMilliseconds`) by a timer, starting hidden behind the pill before its first frame so it never flashes fully open; the timer does not tick headless, so the tests switch the slide off, `PillWindow.SlideEnabled`, in `TestSetup`). It holds `AccountsPanel` in its compact form (`AccountList` rows 54 tall with a budget bar and the play button but not the budget words, in `PillAccountScroll`, which scrolls inside the drawer; there is no Today heading) and, at the top right of the heading, Manage accounts as one sliders icon (`PillManageAccounts`, `IconKind.Sliders`, 28 square, tooltip Manage accounts; there is no button at the foot). Choosing an account leaves it open, so a wrong choice can be put right at once; pressing the button again, Escape or a click elsewhere folds it away (`ShowPanel`, `CloseFlyouts`, which tests call directly because timers do not tick headless); light dismiss has already closed it when a press on the button arrives, so `dismissedAt` stops that same press opening it again. The window never changes size. The right-click menu is `Ui.SettingsMenu`. The whole pill is drawn at 95 per cent of its design size at most, and smaller on a narrow screen (below about 1700 device independent pixels) or a low Windows scale (100 per cent gives 80 per cent, 125 per cent or more gives 95 per cent), because a display with fewer pixels to the inch makes the same pill look bigger (`PillWindow.ScaleFor`, applied by `FitToScreen` through a layout transform). The size is worked out again whenever the pill is shown, when it is dragged onto another screen (`FitIfScreenChanged`, on position changes) and when Windows changes a screen's scale. A size chosen in Settings, Pill size (`TimerModel.PillScalePercent`, 50 to 120 per cent, saved as `pill=NN` or `pill=auto` in the appearance lines) overrides it and applies at once, even while the pill is hidden; with no screen to measure the size is left as it is. The window is always brought to the size the scale calls for by `PillWindow.EnsureSize`, never only when the scale moves (that left a white card under the capsule when the scale was set before the window showed), and it is run after every scale change, when the window opens, when its real size is wrong, and a quarter of a second after the last move of a drag, because Windows ignores size changes during the drag and a pill dragged to another screen would otherwise keep its old window size. The default is System (`ThemeLibrary.Default`), which is Light or Dark by the computer's light or dark setting (`TimerModel.CurrentTheme` resolves it and re-resolves when Windows changes; the app always requests an explicit variant). Two themes ship (`AppThemes.BuiltIn`): Light and Dark, offered with System as three small pictures in Settings, Appearance. After Hours, Botanical, Hawthorn and a user's own themes are retired for now: a saved choice of one becomes Light or Dark by its base (`AppThemes.Resolve`, applied in the `TimerModel` constructor), and the theme itself is left alone in the settings file. Light is `AppThemes.Light`, the shared package's Light with a quiet warm neutral in place of its blue-grey (page `#F4F4F1`, cards `Panel` white, lines `#E2E2DD`, hovers `#EDEDEA`, quiet text `#5A6070`; Ink, the accent and the selection tint are the package's), so the accent is the only blue and the shared package, which the desk app also uses, is unchanged. `ThemeEngine.Write` writes the standard menu resources (`MenuFlyoutPresenterBackground`, the item hover and pressed backgrounds, text, disabled text and separator) from Panel, Hover, Selected, Ink, Muted and Line, so right-click menus follow the theme, and `App.axaml` rounds them (`ContextMenu` 12, items 8). Text boxes and combo boxes follow the mock's field look the same way (`TextControl...` and `ComboBox...` resources: a fill a shade off the card, a hairline, the accent when focused; radius 11 and 12 in `App.axaml`). It also writes `ScrollThumb` and `ScrollThumbHover` (the line colour mixed towards the text colour), which the one slim scroll bar style in `App.axaml` uses everywhere (10 pixels wide, an 8 pixel rounded thumb, no arrows, a transparent track, fading in when the pointer is over the area). `ThemeLibrary.Renamed` maps names that were renamed or removed (Studio, Time Deck, Sage, Ocean and so on) onto Light or Dark by their base. Only a missing theme setting defaults to `ThemeLibrary.Default`; a saved choice is kept. Tests require Ink on Surface and Panel at 7:1, Muted on Surface at 3.5:1 and AccentInk on Accent at 4.5:1 for every built-in, and Ink at 4.5:1 and Muted at 3:1 on the pill's state colours. Writing a theme (`ThemeEngine.Write`) replaces only the resources whose colour changed, because replacing one makes every control using it look again. Timeline blocks are drawn by the theme's block rules (`ThemeDerivation.Block`, via `TimerModel.BlockLook`): the fill is the account colour solid, softened or tinted (`BlockTint` is how much account colour the fill takes), with a gradient to a deeper end (see the timeline paragraph for the corners). Light and Dark both tint their blocks. Charts use `TimerModel.ChartColour`, which is the account's own colour in dark themes because tinted fills sink into the dark surface. Clocks and big numbers use Bricolage Grotesque (SIL Open Font License, `Assets/Fonts`), bundled as three instances cut from the variable font, each its own family (`ClockFont`, `FiguresFont`, `ClockLightFont`, built in `App.Initialize` and used through the `clock`, `figures` and `clockLight` classes).

## UI conventions and pitfalls

- Pop-ups are dialogs, not windows. `Dialog` (in `Dialogs.cs`) is a `ContentControl` with a Title, Width and a `Close()`, shown by the dashboard's `DialogHost` (`DashboardWindow.Dialogs`) on a card over a dim scrim, with the dashboard blurred and unclickable behind it, like the getting started setup. They stack, and Escape or the cross closes the top one before it clears a selection. Every pop-up is one (`EntryDialog`, which is Add time only, `AccountsDialog` and `ShiftDialog`); only the pill and the dashboard are windows. The host draws the card's header (the dialog's Title on the left and the cross on the right) above the dialog's own content, so a dialog does not repeat its title and a scroll bar never runs under the cross. Buttons inside dialogs use `Ui.DialogButton`, which gives the dashboard's quiet outlined look (`toolButton quiet`) and an accent outline on the main action (`mainAction`, for Save, Export and the like). A dialog can refuse to close through its `Closing` event, for one that wants to ask about unsaved edits first. Their height follows their content up to the window. In tests, `TestDialogs.Open` shows a dialog over a dashboard. A hidden dashboard shows no dialog, so the pill's Name and budget menu item asks the model (`TimerModel.OpenAccounts`) and the dashboard comes up first (`DashboardWindow.Reveal`).
- Headings in pop-ups, the settings page and the dashboard use `Ui.Heading`, the `clock` display face, and every button in a pop-up or on the settings page is a `Ui.DialogButton`. Tooltips, notes, refused-edit messages and explainer lines are kept to a short phrase. `WindowCoordinator.KeepInFront` puts a window back at the front of the topmost band when it loses focus and every five seconds while it is not active, because snapping another window over the timer could leave it hidden. Each window can be taken off the topmost band in settings (`TimerModel.PillOnTop` and `DashboardOnTop`, saved as `pilltop=off` and `dashtop=off`), and then `KeepInFront` and `BringToFront` leave it alone. It also does nothing while a topmost window of another app has the focus (`ZOrder.ShouldReassert`, `ZOrder.ForegroundIsTopmost`), or it would jump on top of the screenshot tool's overlay. The cross on the `MessageBar` puts away both the line and the continue offer (until the offer's words change).
- Messages float. `MessageBar` is a toast in the same card as a tooltip (panel colour, a hairline and a soft shadow; a tick on a soft accent circle for something done, a ring with a mark for a refusal or a failed save, since red means overtime, and a heavier edge, `hold`, for a failed save that stays) centred over the lowest part of the Timeline page, over the foot of the Selected block card, so a note, a refused edit or a failed save never moves anything (`review` row 1, always the same place; on the week and settings pages it is over the foot of the workspace). Its style is written `:is(Border).messageBar`, because a plain `Border.x` selector skips a subclass such as `MessageBar`, which once left it with no background; the same goes for `:is(Border).dayCard`, which the Selected block card (a `Border` subclass) wears. Notes and refused edits fade after 15 seconds (`TimerModel.MessageLifetime`), a failed save stays until a save works, and the cross hides it until it changes. An edit that Undo takes back (Merge, Unmerge, Delete: `TimerModel.SayDone`, `NoticeHasUndo`) shows an Undo button in the toast (`UndoMessage`). The Continue earlier block offer lives in the same toast. Edit errors typed into the card (`TimerModel.Refuse`) show here too, and the card's boxes go back to the saved values.
- A selected timeline block is shown by a 3 pixel ring in the theme's accent colour round it (a `BoxShadow` with no blur, so the block's card is not clipped and what is inside it is clipped instead, or the ring is cut off) and is lifted above its neighbours; the `mergeSelected` class stays on the block so it can be found. The older left-edge treatment (`selectedEdge`) is not used on the timeline.
- Settings are a page, not a menu. `SettingsView` fills the dashboard workspace (the gear at the top right of the header, button name `Settings`) and is built once when opened and not rebuilt on model changes. It is a list of sections on the left (`SettingsAppearance`, `SettingsBehaviour`, `SettingsHours`, `SettingsAccounts`, `SettingsExport`, `SettingsAbout`, shown by `ShowSection`) and the chosen section on a card on the right; every section is built once and the others are hidden, so what is being typed in one is kept. Appearance has System, Light and Dark as three small pictures (`ThemeSystem`, `ThemeLight`, `ThemeDark`, the chosen one with an accent border), Pill size as a slider with an Automatic tick (`PillSize`, `PillSizeAutomatic`), Window shadows and Show tooltips; Behaviour has the two on-top switches, Show in taskbar and Start with Windows; Working hours reuses `ShiftEditor`, which is also the working hours window; Hours and accounts has Decimal hours and the Accounts and budgets button. Export holds what the Hours table and Entries views used to carry: Week or Month with a list of periods (`ExportWeekChoice`, `ExportMonthChoice`, `ExportPeriodPick`), Export CSV files (`ExportCsv`, which saves Detail.csv and Summary.csv through `TimerModel.ExportWeek`) and Copy hours table (`CopyHours`, a week only, built by `ReviewViews.WeekTableFor`; `SettingsView.CopiedText` holds what was copied). About has Run setup again, the version and the Development section. The right-click menu (`Ui.SettingsMenu`, whose dividers show only between items that are showing) is Continue earlier block, the version, Test overtime (demo) and Collapse to tray (`TimerModel.RequestHide`, which the coordinator turns into hiding to the tray, or minimising when there is none; Decimal hours lives on the settings page), and the version and Test overtime show only when developer features are unlocked (`TimerModel.DeveloperUnlocked`, saved as `developer=on`; a demo always counts as unlocked; Store builds never unlock, and `StoreBuildTests` proves it by setting `BuildInfo.DeveloperFeaturesOverride` to false, since the tests are built without the Store flag). Ten quick clicks on the About tile in settings unlock them (`SettingsView.UnlockClicks`), and the Development section there (sample-data demo, and a switch to hide them again) appears only when unlocked. In the demo that section is always shown with the switch fixed on and a note instead of the demo button.
- A new database starts with the getting started setup (`OnboardingView`, four steps on a 720 wide card: accounts and optional budgets, working hours, hours format and week start, then a page of things to know with the pill drawn beside it from the same `StatusFace`, for show only; the card has the application icon (the pill outline with its two lights and three bars, in the text colour alone, `SetupPillIcon`) at the top left, the step and its name, and the steps as dots at the right, the current one in the accent and the ones done in a softer accent, with Skip setup at the foot on the left and Back and Next on the right). `StoreSettings.SetupDone` is saved as `setup=done` or `setup=pending` in the appearance lines. A database with neither line counts as done, unless it was just created, so existing users never see it. `DashboardWindow.UpdateOnboarding` lays it over the dashboard, which is blurred and not clickable while it shows, and `App` opens the dashboard first when the setup is pending. Each step applies on Next, and Skip setup or Esc finishes it, leaving the starting accounts alone. Controls on a step must be detached from their old parent when a step is rebuilt (`Detach`). Settings has Run setup again (`TimerModel.RestartSetup`). Tests that use a real new database should call `CompleteSetup` or the overlay will catch their clicks.
- Accounts can be deleted from Accounts and budgets (the bin on each row marks it, and Save does it). `TimerModel.SetAccounts` takes a `deleted` list, and `LedgerEditor.DeleteAccount` removes the account's entries, notes and groups and clears the Undo history, like a rename. An account with recorded time asks for confirmation in the window first (`DeleteConfirm`), a `before-delete` backup is saved, and a running account is stopped. Removing an account from the list any other way is still refused, so it has to be hidden instead.
- Every window calls `WindowChrome.Attach(this)`, which gives it the app icon and, on Windows 11, a title bar in the theme's colours that follows theme changes and previews (`ThemeEngine.Applied`). Older Windows keeps its normal title bar.
- There is no Adjust time feature. Databases made while it existed are cleaned when they open: `TimerStore` leaves `adjustment` rows out, keeps a `before-removing-adjustments` backup, drops their notes and clears the undo history (`AdjustmentsRemoved` drives a notice). The schema's `adjustment` kind is left in place, since SQLite cannot drop a CHECK value cheaply.
- The app icon is one drawing in one colour (`Assets/AppIcon.png` and `AppIcon.ico`, and the Store tiles in `migration/packaging/StoreAssets`, cut from it): the pill as a line outline with its two lights and bars for the hours, minutes and seconds, near black on a white tile; the sizes up to 32 pixels use a thicker outline, bigger lights and no seconds bar (`docs/redesign/mock/Icon.dc.html` has the drawing). The tray icon is the same mark with no tile (`TrayController.Draw`), white on a dark taskbar and near black on a light one by the computer's own setting, with the state light green while recording and the reminder light blue while a reminder is due.
- The taskbar button is on by default and `TaskbarButton` can be switched off only once the tray exists (`TrayAvailable`).
- Use the helpers in `Controls.cs` (`Ui.Grid`, `Ui.Put`, `Ui.Button`, `Ui.IconButton`, `Ui.Text`). Style through classes in `App.axaml` and `DynamicResource` theme tokens rather than hard-coded colours.
- `Ui.Visible` lifts very dark account colours so dots and blocks stay visible on dark themes; `Ui.InkOn` picks text for a block.
- Controls that draw themselves with `TryFindResource` (`IconGlyph`, `Chevron`, `PauseGlyph`, `BreakGlyph`, `AccountIndicator`, `BudgetBar`) must call `InvalidateVisual` when `ActualThemeVariant` changes, because the pill changes variant with its state and a stale brush can be unreadable. Tray menu items (`TrayController`) need their words set at construction, not only on the menu's Opening event.
- Slider colours come from `ThemeEngine.SliderColours` (an empty track that holds 3 to 1 on Surface and Panel, and a fill and thumb in the accent unless it is too faint), not from the theme's Line, which is only a hairline. ## Keeping builds few

Each merge into `experimental` or `alpha` builds and stores a Windows ZIP (kept 14 days), and a pull request run adds tests on Windows. A manual run of the workflow (Run workflow, or the API) on any other branch keeps its own ZIP for 7 days, named for the branch, so a feature branch can be tried without a merge. The owner tests only every few versions, so batch work: keep related changes on one `feature/...` branch, open one pull request for the lot, and sync `experimental` only for a candidate. Before opening a pull request for a small change, ask whether it can wait for the next one. Rendered previews upload only when a test fails or a run is started by hand.

## Checking changes

Run `dotnet test migration/tests/Timer.Desktop.Tests -c Release`. CI runs it on Windows only and publishes a self-contained Windows build; check the run before saying tests pass. A test that fails now and then is a defect to find, never to re-run past: **Repeat the tests (manual)** (`test-repeat.yml`: Run workflow with a number of times, available once the file is on `main`; a pull request that changes the file runs it too, eight times) runs the whole suite again and again on one build and lists which tests failed in which runs. Headless input is hit-tested against the last rendered frame, so the tests' `RobustFrames` and `RobustInput` (more specific `CaptureRenderedFrame`, `MouseDown`, `MouseMove` and `MouseUp`, found before Avalonia's own) make sure a frame has rendered first, because a slow Windows runner can lag. The user tests visuals on Windows and reports back with screenshots.

## Timeline viewport behaviour

`ReviewViews.Timeline` adjusts only the render transforms of partly visible hour labels (an X shift) to keep the full labels inside the viewport. Canvas block positions, ticks and pointer-to-time calculations stay unchanged; the ScrollViewer clips at both edges. The default scroll anchor is the earliest recorded block (a little way in from the left), with the working-day start as fallback. An explicit `TimelineOffset` (a horizontal offset) always takes precedence. Do not add offsets to block geometry to compensate for label placement.
