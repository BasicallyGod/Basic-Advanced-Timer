# Basic’s Advanced Timer: engineering notes

Notes for contributors and coding assistants. The application is a C# Avalonia desktop app on .NET 8, always on top, for tracking time against client accounts and preparing timesheets. It must run without installs or administrator rights. The earlier PowerShell/WinForms app (v2.32) was removed from the tree and lives in Git history.

## Branches and releases

`main` is the Store release, `experimental` is everyday testing and `alpha` is for risky prototypes. Work on `experimental` or a `feature/...` branch from it, promote alpha to experimental and experimental to main by pull request, and never push straight to `main`. Builds show their channel beside the version, and only non-Store builds offer the sample-data demo. The updater serves experimental and alpha only, each with its own data, versions and backups. See `BRANCHES.md`.

## Behaviour to preserve

- **Working time and allocation.** Reports show Working time as Allocated (time on accounts) plus Unallocated (working clock time not on any account, never below zero), with Breaks separate and not counted. The running entry's elapsed time is included (`TrackingEngine.ActiveElapsedOn`). Budget figures for an earlier week use that week's own period (`TimerModel.BudgetReference`, `BudgetUsedAt`, `BudgetPeriodNameAt`, the Thursday rule), never "this month". Hiding an account (In tracker) only removes it from the tracker list. Its time stays in `ReviewAccounts` and every report. Scroll views that end above fixed controls use `Ui.WithMoreBelow`, which draws a one pixel line in the theme's Line colour along the edge with more content past it, below and, once scrolled, above (a fade or shadow looked muddy on light themes).
- **Colour roles.** Green (`Live`) means tracking only, the accent means selection, focus and the main action (a blue in Light and Dark, kept clear of red, green and orange), amber means a break, `BudgetWarning` means a budget at 80 per cent and red (`Overtime`) means overtime or a spent budget. A budget bar with room left is neutral (`Muted`), the setup's current step dot is the accent, and the idle pill dot is `Idle`.
- **Duration format.** Every duration reads as HH:MM (`TimerModel.Format`, `FormatShort` and `FormatCompact` all give 01:30), and as decimal hours when that is chosen. Do not add a new way of writing one.
- **Credited totals.** Entries hold credited durations. Totals come from credited seconds, never from clock spans. Positioning credit never adds hours; "Add time" does.
- **Day clock.** The main clock is working plus overtime time, excluding Lunch, breaks and away. Stopping or switching an account does not reset it. Scheduled starts are automatic. A day off counts only tracked time. `SetShifts` drops manual starts the new hours make unnecessary. `ResumeAfterBreak` is stored with the running row. `BreakAccount.Name = "Break"` is reserved.
- **Exact decimal hours.** Exports apportion hundredths of an hour by largest remainder, first across account/day totals and then within each bucket, so every sum is exact. Running totals are provisional until saved.
- **Gaps.** Selected gaps are validated against the unrounded current gap before being moved to whole seconds, because durations use hundredths of a minute. Tidy day rechecks the whole selection before adding anything, as one undo step.
- **Switching accounts.** A block's length is kept to hundredths of a minute and its start to the second, so `TrackingEngine.ToggleAccount` starts the new block at the whole second after the old one's stored end when needed, and consecutive blocks never overlap. The timeline also treats blocks within two seconds as meeting, so older overlaps do not split the day into lanes. After a quick slip from one account to another and back (a block of three minutes or less, switched back within three minutes, `TrackingEngine.ContinuableBlocks`), `ContinuePrevious` drops the short block and reopens the earlier one so it carries on as one, with the slip's time. It is offered in the dashboard footer, the pill's list, the right-click menu and the recording block's menu, and not for blocks in a group. Pressing play on an account whose block the time now falls inside (one added or pasted ahead of time) carries that block on instead of starting a second one on top of it (`TrackingEngine.FutureBlockOf`, `ContinuedBlock`): it is reopened from its own start, stopping ends it where the recording stops, and it is skipped for a block in a group or one that would overlap other recorded time. A break is carried on the same way, so starting a break inside a break block already there reopens it.
- **Selecting and opening timeline blocks.** Clicking a block selects or deselects it (so two clicks make a pair to merge), and there is no double-click to edit, which could not be told apart from two clicks and once opened the wrong account. The Edit button in the bar under the workspace (`EditSelected`, called Inspect for a group, shown when exactly one block is selected, `TimerModel.EditSelection`), Enter, and the right-click menu open the editor. Double-clicking empty space still adds time.
- **Dragging to a neighbour.** A block's end is kept to the whole second and its length to hundredths of a minute, so `TimelineGestures` snaps an edge to the neighbour's start with `LastDeltaBefore`, which steps back a second at a time until the saved block really ends no later than it. This matters most for the block being recorded, whose start has a fraction of a second.
- **Undo.** Edits are stored as splices plus hashes in `edits` and `edit_changes`, so history stays small and survives restarts.

## Storage

`TimerDatabase` holds accounts, entries, groups, away, day_starts, running, edits, edit_changes and meta. It takes an exclusive lock, uses WAL and `user_version`, and makes daily backups. The schema is format 2 (a budget can be per day), and `TimerDatabase.Upgrades` holds the numbered steps that take an older file forward after a copy is saved; a step that rebuilds a table runs with foreign keys off and is checked with `foreign_key_check` before it is kept, and an older build refuses a newer file. Dispose every `SqliteCommand` or Windows keeps the file locked, which fails tests on CI. `TimerStore` rewrites `entries` when a snapshot changes. Notes, groups and `accountsSeeded` are blobs in `meta`. The settings JSON preserves unknown sections and is swapped in atomically with a `.bak`. Sessions checkpoint every 15 seconds and recovery stops at the last checkpoint. `TimerStore` refuses a folder holding the old `AccountTimer2.ps1` or launcher, and the old CSV files are deliberately never imported. Never auto-open another app's data folder. Never commit `migration-data`, `timer.db`, settings JSON or logs (`.gitignore` excludes them).

## Themes

Each theme is a `ThemeDefinition` (name, Light or Dark base, colour tokens, block style) and an Avalonia `ThemeVariant`. `ThemeTokens.Names` lists the tokens (Surface, Panel, Ink, Muted, Line, Hover, Selected, Live, Idle, Overtime, BudgetWarning, Break, Finish, Start, Accent, AccentInk, Clock, PillSurface, PillInk, PillBreak, PillOvertime, ShadowColor). `ThemeEngine.Register` writes brushes into `Application.Resources.ThemeDictionaries` in place so open windows repaint. Built-ins register in `App.Initialize`, user themes in the `TimerModel` constructor and on save. The pill is a rounded card (24 pixel corner, with the account's colour in a rounded badge, `PillBadge`) that wears its state: the normal theme when idle, the theme's pill colour while recording, its pill break colour on a break and its pill overtime colour in overtime (`ThemeDerivation.Variant`, registered as `Recording`, `Break` and `Overtime` variants, with break outranking overtime outranking recording). Text, lines and hovers inside it are mixed from the capsule colour and its text colour, and the colours that normally carry meaning (break, overtime, finish) become that text colour. Capsule colours that are too dull to carry text are brightened (`ThemeLibrary.Capsule`), and a dark theme's overtime colour is deepened. The pill is 82 high and grows taller when opened, keeping its corner. Its width and arrangement come from the chosen layout (`PillLayouts`, `TimerModel.PillStyle`, saved as `pillstyle=compact|minimal` through the library's extras, with no line for Full, and picked in Settings, Appearance and behaviour, from three small pictures named `PillLayout_<key>`): Full is 516 wide with the clock first, the account, today's time and the day's progress line; Compact is 520 wide with the account first, then the clock, and no progress line; Minimal is 360 wide with a badge of the account's initials (the amber dot on a break), the clock and pause, and no break button, since Start break is on the right-click menu. `PillWindow.ApplyLayout` rearranges the same controls for each, and the window is the same width open or closed, so opening the list never moves it sideways. An open pill is at most three fifths of the screen's height (`PillWindow.OpenShareOfScreen`): the account list scrolls inside its own box (`PillAccountScroll`, `ListMaxHeight`) so Finish day stays in view. With nothing running the pill says what it waits for: the chosen account with Ready to track, or Ready to track with Select an account when none is chosen. The whole pill is drawn at 85 per cent of that at most, and smaller on a narrow screen (below about 1500 device independent pixels) or a low Windows scale (100 per cent gives 70 per cent, 125 per cent or more gives 85 per cent), because a display with fewer pixels to the inch makes the same pill look bigger (`PillWindow.ScaleFor`, applied by `FitToScreen` through a layout transform). The size is worked out again whenever the pill is shown, when it is dragged onto another screen (`FitIfScreenChanged`, on position changes) and when Windows changes a screen's scale. A size chosen in Settings, Pill size (`TimerModel.PillScalePercent`, 50 to 120 per cent, saved as `pill=NN` or `pill=auto` in the appearance lines) overrides it and applies at once, even while the pill is hidden; with no screen to measure the size is left as it is. The window is always brought to the size the scale and state call for by `PillWindow.EnsureSize`, never only when the scale moves (that left a white card under the capsule when the scale was set before the window showed), and it is run after every scale change, when the window opens, when its real size is wrong, and a quarter of a second after the last move of a drag, because Windows ignores size changes during the drag and a pill dragged to another screen would otherwise keep its old window size. The default is System (`ThemeLibrary.Default`), which is Light or Dark by the computer's light or dark setting (`TimerModel.CurrentTheme` resolves it and re-resolves when Windows changes; the app always requests an explicit variant). Five built-ins ship: Light (the former Studio palette, worked out by `ThemeLibrary.Themed`) and Dark, and the studies After Hours, Botanical and Hawthorn (add more to `ThemeLibrary.BuiltIn` and every list picks them up). A study is set by hand from six colours (surface, panel, text, accent, break, overtime) plus the tracking green, and `ThemeLibrary.Themed` works out quiet text, lines, hovers and selection so each holds the contrast tests. They have no per-theme account palettes yet. `ThemeLibrary.Renamed` maps names that were renamed or removed (Studio, Time Deck, Sage, Ocean and so on) onto Light or Dark by their base. Only a missing theme setting defaults to `ThemeLibrary.Default`; a saved choice is kept. Tests require Ink on Surface and Panel at 7:1, Muted on Surface at 3.5:1 and AccentInk on Accent at 4.5:1 for every built-in, and Ink at 4.5:1 and Muted at 3:1 on the pill's state colours. Writing a theme (`ThemeEngine.Write`) replaces only the resources whose colour changed, because replacing one makes every control using it look again, and a preview (`TimerModel.PreviewTheme`, `ThemeEngine.RegisterPreview`) writes only the main variant, not the pill's tinted ones. The theme editor shows its first change at once and gathers the rest to at most one repaint every 70 ms, builds each colour picker only when it first opens (a `ColorSpectrum` wheel in ring shape, a `ColorSlider` bar for lightness and a hex box, from the `Avalonia.Controls.ColorPicker` package, whose styles are included in `App.axaml` because FluentTheme does not load them), and putting the saved look back after a preview re-registers just the theme that was edited. Built-ins are locked in the editor; the editor asks before discarding unsaved edits. Every timeline block has the same corner (`ReviewViews.BlockRadius`, 6, less only for a block too short to hold it). Timeline blocks are drawn by the theme's block rules (`ThemeDerivation.Block`, via `TimerModel.BlockLook`). The style is solid (the account colour), softened, or tinted (`BlockTint` is how much account colour the fill takes and `BlockEdge` how far the left edge moves towards the text colour), and every block has a strip down its left side. Light and Dark both tint their blocks. Charts use `TimerModel.ChartColour`, which is the account's own colour in dark themes because tinted fills sink into the dark surface. Clocks and big numbers use Bricolage Grotesque (SIL Open Font License, `Assets/Fonts`), bundled as three instances cut from the variable font, each its own family (`ClockFont`, `FiguresFont`, `ClockLightFont`, built in `App.Initialize` and used through the `clock`, `figures` and `clockLight` classes).

## UI conventions and pitfalls

- Pop-ups are dialogs, not windows. `Dialog` (in `Dialogs.cs`) is a `ContentControl` with a Title, Width and a `Close()`, shown by the dashboard's `DialogHost` (`DashboardWindow.Dialogs`) on a card over a dim scrim, with the dashboard blurred and unclickable behind it, like the getting started setup. They stack, and Escape or the cross closes the top one before it clears a selection. Every pop-up is one (`EntryDialog`, `TidyDialog`, `GroupDialog`, `ExportDialog`, `AccountsDialog`, `ShiftDialog` and `ThemesDialog`); only the pill and the dashboard are windows. The host draws the card's header (the dialog's Title on the left and the cross on the right) above the dialog's own content, so a dialog does not repeat its title and a scroll bar never runs under the cross. Buttons inside dialogs use `Ui.DialogButton`, which gives the dashboard's quiet outlined look (`toolButton quiet`) and an accent outline on the main action (`mainAction`, for Save, Export and the like). A dialog can refuse to close through its `Closing` event, which is how the theme editor asks about unsaved edits. Their height follows their content up to the window. In tests, `TestDialogs.Open` shows a dialog over a dashboard. A hidden dashboard shows no dialog, so the pill's Name and budget menu item asks the model (`TimerModel.OpenAccounts`) and the dashboard comes up first (`DashboardWindow.Reveal`).
- Headings in pop-ups, the settings page and the dashboard use `Ui.Heading`, the `clock` display face, and every button in a pop-up or on the settings page is a `Ui.DialogButton`. Tooltips, notes, refused-edit messages and explainer lines are kept to a short phrase. `WindowCoordinator.KeepInFront` puts a window back at the front of the topmost band when it loses focus and every five seconds while it is not active, because snapping another window over the timer could leave it hidden. Each window can be taken off the topmost band in settings (`TimerModel.PillOnTop` and `DashboardOnTop`, saved as `pilltop=off` and `dashtop=off`), and then `KeepInFront` and `BringToFront` leave it alone. It also does nothing while a topmost window of another app has the focus (`ZOrder.ShouldReassert`, `ZOrder.ForegroundIsTopmost`), or it would jump on top of the screenshot tool's overlay. The cross on the `MessageBar` puts away both the line and the continue offer (until the offer's words change).
- Messages float. `MessageBar` sits centred over the lowest part of the workspace, above the buttons, so a note, a refused edit or a failed save never moves the buttons. It has its own raised look (`messageBar`, panel colour, accent outline and a shadow) so it shows against any block. Its style is written `:is(Border).messageBar`, because a plain `Border.x` selector skips a subclass such as `MessageBar`, which once left it with no background. Notes and refused edits fade after 15 seconds (`TimerModel.MessageLifetime`), a failed save stays until a save works, and the cross hides it until it changes. The Continue earlier block button lives in the same bar. Selection feedback is not a message. `SelectionStrip` is a quiet strip in the layout just above the Add time, Undo and Merge buttons (panel colour, a hairline on top, nothing in the accent colour). It shows the count (`TimerModel.SelectionCountText`), one short note naming the specific merge problem (`SelectionNote`) and a Clear selection text button. The full merge rule lives in the Merge tooltip (`MergeHint`).
- A selected block or entry is shown by its left edge in the theme's accent colour, a little wider (`selectedEdge`), with no outline. The `mergeSelected` class stays on the block so it can be found.
- Settings are a page, not a menu. The theme list there refreshes when themes are saved or deleted. `SettingsView` fills the dashboard workspace (rail gear, button name `Settings`), is built once when opened and not rebuilt on model changes, and reuses `ShiftEditor`, which is also the working hours window. The right-click menu (`Ui.SettingsMenu`, whose dividers show only between items that are showing) is Start or End break and Add note… (Quick capture, below), then Continue earlier block, the version, Test overtime (demo) and Collapse to tray (`TimerModel.RequestHide`, which the coordinator turns into hiding to the tray, or minimising when there is none; Decimal hours lives on the settings page), and the version and Test overtime show only when developer features are unlocked (`TimerModel.DeveloperUnlocked`, saved as `developer=on`; a demo always counts as unlocked; Store builds never unlock, and `StoreBuildTests` proves it by setting `BuildInfo.DeveloperFeaturesOverride` to false, since the tests are built without the Store flag). Ten quick clicks on the About tile in settings unlock them (`SettingsView.UnlockClicks`), and the Development section there (sample-data demo, and a switch to hide them again) appears only when unlocked. In the demo that section is always shown with the switch fixed on and a note instead of the demo button. The demo also holds sample notes and reminders (`TimerModel.SeedDemoNotes`, written in the Notes shorthand: tasks, a timed event and a `!` deadline today, tagged ones, and dated ones out to about five months) so Notes and Coming up are not empty; they live in memory or the throwaway database only.
- A new database starts with the getting started setup (`OnboardingView`, four steps: accounts and optional budgets, working hours, hours format and week start, then a page of things to know). `StoreSettings.SetupDone` is saved as `setup=done` or `setup=pending` in the appearance lines. A database with neither line counts as done, unless it was just created, so existing users never see it. `DashboardWindow.UpdateOnboarding` lays it over the dashboard, which is blurred and not clickable while it shows, and `App` opens the dashboard first when the setup is pending. Each step applies on Next, and Skip setup or Esc finishes it, leaving the starting accounts alone. Controls on a step must be detached from their old parent when a step is rebuilt (`Detach`). Settings has Run setup again (`TimerModel.RestartSetup`). Tests that use a real new database should call `CompleteSetup` or the overlay will catch their clicks.
- Accounts can be deleted from Accounts and budgets (the bin on each row marks it, and Save does it). `TimerModel.SetAccounts` takes a `deleted` list, and `LedgerEditor.DeleteAccount` removes the account's entries, notes and groups and clears the Undo history, like a rename. An account with recorded time asks for confirmation in the window first (`DeleteConfirm`), a `before-delete` backup is saved, and a running account is stopped. Removing an account from the list any other way is still refused, so it has to be hidden instead.
- Every window calls `WindowChrome.Attach(this)`, which gives it the app icon and, on Windows 11, a title bar in the theme's colours that follows theme changes and previews (`ThemeEngine.Applied`). Older Windows keeps its normal title bar.
- There is no Adjust time feature. Databases made while it existed are cleaned when they open: `TimerStore` leaves `adjustment` rows out, keeps a `before-removing-adjustments` backup, drops their notes and clears the undo history (`AdjustmentsRemoved` drives a notice). The schema's `adjustment` kind is left in place, since SQLite cannot drop a CHECK value cheaply.
- The taskbar button is on by default and `TaskbarButton` can be switched off only once the tray exists (`TrayAvailable`).
- Use the helpers in `Controls.cs` (`Ui.Grid`, `Ui.Put`, `Ui.Button`, `Ui.IconButton`, `Ui.Text`). Style through classes in `App.axaml` and `DynamicResource` theme tokens rather than hard-coded colours.
- `Ui.Visible` lifts very dark account colours so dots and blocks stay visible on dark themes; `Ui.InkOn` picks text for a block.
- Controls that draw themselves with `TryFindResource` (`IconGlyph`, `Chevron`, `PauseGlyph`, `BreakGlyph`, `AccountIndicator`, `BudgetBar`) must call `InvalidateVisual` when `ActualThemeVariant` changes, because the pill changes variant with its state and a stale brush can be unreadable. Tray menu items (`TrayController`) need their words set at construction, not only on the menu's Opening event.
- Slider colours come from `ThemeEngine.SliderColours` (an empty track that holds 3 to 1 on Surface and Panel, and a fill and thumb in the accent unless it is too faint), not from the theme's Line, which is only a hairline. Sliders in a built-in theme's editor are disabled, so the `...Disabled` slider resources are written too (`ThemeEngine.DisabledSliderColours`). Repeating keyframe animations (`Ui.Pulse`, `BreakGlyph.SetSteaming`) are kept as a `RunningAnimation`, so one that stopped by itself is started again when asked for; a task that is already complete at start (headless tests, where nothing ticks) counts as running.
- Drag handlers mark presses as handled, so they must call `Ui.CloseMenus` first or an open right-click menu stays open.
- Tooltips take their colours from the theme (`ToolTipBackground`, `ToolTipForeground` and `ToolTipBorderBrush` are written from Surface, Ink and Line for every theme and pill state in `ThemeEngine.Write`), so they never show dark text on a dark tooltip. In the pill, the account name and the second line are `AutoScrollText` inside a `NameRow`, which slide to their end and back when too long, and the chevron stays beside the name. The older `MarqueeText` is the hover scroll in account lists.
- Tooltips can be switched off in settings (`TimerModel.Tooltips`, saved as `tooltips=off` in the appearance lines). `Ui.ApplyTooltips` adds one class handler that cancels `ToolTip.ToolTipOpeningEvent`, which is a direct event, so a handler on the window would never see it. The Live token is green (tracking), and the recording pill lifts it to read on its dark surface (`ThemeDerivation.Variant`). Add time, Undo, Merge and Edit share the bar under the workspace with the zoom controls, whose slider shrinks to leave room for them (`TheToolbarButtonsNeverRunUnderTheZoomControls` checks every selection).
- Notes (`NotesPage` in `NotesView.cs`, the `NotesTab` button, second on the rail, in the top group with Timeline and Week overview (Hours table and Entries sit below a divider), `DashboardWindow.ShowNotes`, `notesMode`) is a page like Settings: built once when it opens and not rebuilt on model changes, because it listens to the model itself and rebuilds only when what it shows changed (`Signature`), and not at all while a note's words are being edited (it waits until the box is left), so a tick of the clock or a save never interrupts typing. It shows the notes for `TimerModel.SelectedDate` (the date arrows still work) beside Coming up (`ComingUpView`). A note is typed in the shorthand from `Timer.Core` (`NoteShorthand`: a time such as 14:30, `@fri` or `@tomorrow` for a day, a leading `!` for a deadline, `#AccountOne` linking an account through `AccountTags`), and the shorthand still works in the quick box at the foot of the page (`NoteInput`, watermark "Quick add"), but nothing depends on it: Add note (`NoteAddButton`) and each row's Details (`NoteDetails_<id>`, shown on hover) open the same flyout (`NoteDetails` in `NoteDetails.cs`, built each time it opens) with a Task, Meeting or Deadline switch (`NoteKind_Task`, `_Meeting`, `_Deadline`), the words, the day (arrows and an inline calendar, never a second pop-up inside the flyout), start and end (`NoteDetailsStart`, `NoteDetailsEnd`, HH:mm), the account, Repeat (Never, Every day, Every weekday, Every week, Every 2 weeks, or Choose days, with `NoteDetailsUntil`), and for a note in a series Apply changes to This one only or This and all later (only the second can change the repeat), then Save or Add (`NoteDetailsSave`, `NoteDetailsAdd`) and Remove… (a series asks which). `TimerModel.AddNote`/`SaveNote` take a `NoteEdit` and return what is wrong (a meeting needs a start, an end after it, times as HH:mm) or null. A row is one line (the "one line" design: tick box, words, then quiet marks on the right: `NoteTime_<id>`, a flag `NoteDeadlineMark_<id>`, the repeat mark `NoteRepeatMark_<id>`, and the account's dot `NoteAccountMark_<id>`; the Details and remove buttons carry the `hoverReveal` class). The words box shows the words without the `!` and the `#Tag` (`NoteShorthand.Display`) and `SetDayNoteWords` puts them back around what is typed. The crosses and the move-day calendar are gone from the row (the day is changed in Details; `ClearNoteTime`, `ClearNoteDeadline` and `ClearNoteAccount` stay on the model). The remove and Details buttons (the `hoverReveal` class; `Ui.RevealOnHover` puts a `revealing` class on the row) show only while the row is under the pointer or has focus, so a list of notes is words first. The headings in both cards are plain semibold text, not the display face, and Coming up is grouped under a heading per day with each row showing only its time. Each note has a tick box (`NoteTick_<id>`), editable words (`NoteText_<id>`) and a remove button (`NoteRemove_<id>`). Notes live in the database (`day_notes`, outside the undo history) through `TimerModel` (`AddDayNote`, `NotesOn`, `ComingUp`, `ClearNoteTime`, `ClearNoteDeadline`, `ClearNoteAccount`, `MoveDayNote`, `ToggleDayNote`, `SetDayNoteText`, `RemoveDayNote`), and `SetAccounts` rewrites a renamed account's tags and turns a deleted account's into plain words. Account-coloured tag text uses `TagColours.Text`. Typing a `#` in the add box (and in Quick capture) lists the accounts that match (`TagPicker`, `TagSuggestions` in `TagPicker.cs`): the arrow keys move, Tab or Enter completes the chosen tag (Enter completes rather than saves while the list is open), Escape or a finished tag puts it away, and the Break account is never offered. A note can go on any day: the small calendar beside the box (`NoteDayPick`) picks the day for the next note, shown as a chip (`NoteDayChip`, `NoteDayClear`) until it is added, and a day typed in the words still wins; pressing the date in the header (`DatePick`, `TimerModel.GoToDate`, which on the week views will not pass the current week) opens a calendar that jumps to any day; and Coming up looks 180 days ahead (`TimerModel.ComingUp`). The Missed tab (`TimerModel.MissedNotes`, `MoveMissedToToday`, button `NotesMissedToToday`) lists tasks and deadlines from the last 90 days that were never ticked off, grouped by day, with one button to carry them to today; an event just passes, so it is never missed. Removing a note keeps it for Undo remove (`NoteUndoRemove`, `TimerModel.RestoreRemovedNote`, the last 20). A note the database refuses never crashes the app or leaves the screen: it keeps a negative id and is written again with every save (`NoteStore`, `RetryNoteWrites`, `NotesUnsaved`), with a notice (said again only when its words change). This is kept apart from `LastError`, which the account and entry dialogs read to decide whether their own save failed. Reminders (`Reminders.cs`, `ReminderRules`, `ReminderCard`; `TimerModel.Reminders`, `ActiveReminder`, `SnoozeReminder`, `DoneReminder`, `ReminderDue`, `NotesRequested`): a note with a time, or a `!` deadline (17:00 when it has none), is Soon for the lead time before it (a quiet dot on the Notes rail button, 10 minutes by default, 0 for none), Due for five minutes after (a card with Snooze and Done), then Overdue until ticked off, and it looks back 24 hours so one that fell due while the app was closed still shows. A ticked note never reminds, Snooze (kept in the settings file as `remindsnoozed=id:ticks,...`, so a restart does not bring it straight back) hides it for the snooze time and then it is Due again, and the check runs on every `Tick` and notifies only when the set of states changes. The card is `ReminderCard`: a floating `messageBar` above the message line on the dashboard (red outline when overdue, `late` class), and a row under the capsule in the pill (`reminderHost`, its own grid row, so the pill's width never changes and `WantedHeight` adds its height; the pill becomes a card shape while it shows, `ApplyShape`). Pressing its words opens Notes (`RequestNotes`), and a reminder falling due while the timer is tucked away brings the pill back. Settings, Reminders, holds the on/off switch, heads-up and snooze times (saved as `remind=off`, `remindlead=N`, `remindsnooze=N`). A due reminder plays the system alert sound once (`ReminderSound`, `TimerModel.ReminderSoundOn`, saved as `remindsound=off`, a switch in Settings, Reminders), and restores a timer that was only minimised (`WindowCoordinator.BringBackForReminder`, since a minimised window still counts as visible, which is how the timer is tucked away without a tray). There is no Windows notification. Everything waiting is also one list (`NotificationsPanel` in `Notifications.cs`, built each time its flyout opens and following the model while open): "Needs attention" (overdue, due, and a meeting's "did it take place?") above "Coming up" (heads-ups), each row with its own buttons (`NotificationItem_<id>`, `NotificationSnooze_<id>`, `NotificationDone_<id>`, `NotificationNo_<id>`, `NotificationYes_<id>`). It opens from the bell at the left of the dashboard header's date controls (`NotificationsBell`, with a count badge `NotificationsBadge` that goes red when anything is overdue) and from "+2 more" on a reminder card (`ReminderMore`, which counts the other reminders, `TimerModel.MoreReminders`), so the pill's capsule never gains a button and its width never changes. Snooze on a card and in the list is a drop-down of the Settings choices (`ReminderUi.SnoozeButton`, `ReminderSnooze_<minutes>`, `TimerModel.SnoozeReminder(id, minutes)`), and a meeting's question can be put off the same way (the "…" on the timeline prompt). A heads-up shows on the pill only when Settings, Reminders, "Show a reminder on the pill before it is due" is on (`TimerModel.ShowUpcoming`, saved as `remindupcoming=on`, off by default). While the dashboard shows the timeline (`TimerModel.TimelineVisible`) a meeting's question is drawn on it, under the block (`TimelinePrompt_<id>`, `TimelinePromptNo_<id>`, `TimelinePromptYes_<id>`, `TimelinePromptLater_<id>`), and the floating card (`TimerModel.DashboardReminder`) leaves out that day's question so it is not asked twice. The main action of a panel (Add note, Save) is solid in the accent colour (the `primary` class on a `toolButton`); other buttons keep the quiet outline. A meeting is a note typed with a start and a later end (`14:00 - 15:30`, a hyphen or dash; `DayNote.End`, `DayNotes.IsMeeting`, `end_time` in `day_notes` from format 4 of the shared storage, so it needs `BasicallyGod.Timer.Core` and `Timer.Storage` 0.3.0 or later). It shows as 14:00–15:30 (`NoteTimes.Of`), reminds before it like any timed note, is never Overdue while it is under way, and is drawn on the timeline as planned time (`TimerModel.MeetingsOn`, a dashed outline named `TimelineMeeting_<id>` in its own lane down the right-hand side so tracked time never hides it, never counted in any total). When it ends it asks once, on the usual reminder card, whether it took place (`ReminderState.Followup`, buttons No and Yes on `ReminderSnooze` and `ReminderDone`): No ticks the note off, Yes opens Add time on its hours (only the free part when some of it is already recorded, which stays as it was; none left ticks it off at once) with the account its `#Tag` names chosen (`TimerModel.LogMeeting`, `FreeParts`, `TakeEntryAccountHint`, `EndMeetingLog`), and saving that entry ticks the note off, so the planned block gives way to tracked time. An unanswered question stays until answered, for up to a day. A note repeats when its words hold an `every` phrase (`every day`, `every weekday`, `every mon`, `every mon,wed,fri`, `every week`, `every 2 weeks fri`, each with an optional `until 2026-12-31`; always spelled with "every", never a bare "daily"; `Recurrence` and `NoteSeries` in `Timer.Core`, format 5 of the shared storage, so it needs the packages at 0.4.0 or later). A repeat is a series (the template, its rule and `GeneratedTo`, the last day notes were made for) and ordinary dated notes that carry its id (`DayNote.SeriesId`), made from today up to eight weeks ahead when the note is added, when the app starts and each day (`TimerModel.MakeSeriesNotes`, never filling in the past), so every occurrence can be moved, ticked, answered (a No on a meeting skips only that day) or removed alone, and a removed one is not made again because `GeneratedTo` has passed it. Removing a note that repeats asks Remove this one (`NoteRemoveOne_<id>`, or `NoteDetailsRemoveOne` in Details) or This and all later (`NoteRemoveLater_<id>`, `NoteDetailsRemoveLater`, `RemoveSeriesFrom`, which ends the series the day before, or deletes it when nothing earlier is left). The repeat mark on a row names the rule in its tooltip, and the rule is changed in Details (choosing This and all later). `ClearNoteRepeat` and `ApplyToLater` remain on the model. Editing a note's words in its row changes that one only. Coming up shows a series once, as its next time, and the Missed tab leaves repeats out, since the next one is already there. Renaming or deleting an account follows into the template too.

## Keeping builds few

Each merge into `experimental` or `alpha` builds and stores a Windows ZIP (kept 14 days), and a pull request run adds tests on Windows. The owner tests only every few versions, so batch work: keep related changes on one `feature/...` branch, open one pull request for the lot, and sync `experimental` only for a candidate. Before opening a pull request for a small change, ask whether it can wait for the next one. Rendered previews upload only when a test fails or a run is started by hand.

## Checking changes

Run `dotnet test migration/tests/Timer.Desktop.Tests -c Release`. CI runs it on Windows only and publishes a self-contained Windows build; check the run before saying tests pass. A test that fails now and then is a defect to find, never to re-run past: **Repeat the tests (manual)** (`test-repeat.yml`: Run workflow with a number of times, available once the file is on `main`; a pull request that changes the file runs it too, eight times) runs the whole suite again and again on one build and lists which tests failed in which runs. Headless input is hit-tested against the last rendered frame, so the tests' `RobustFrames` and `RobustInput` (more specific `CaptureRenderedFrame`, `MouseDown`, `MouseMove` and `MouseUp`, found before Avalonia's own) make sure a frame has rendered first, because a slow Windows runner can lag. The user tests visuals on Windows and reports back with screenshots.

- Test with synthetic data only.
