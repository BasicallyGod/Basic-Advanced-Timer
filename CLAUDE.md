# Basic’s Advanced Timer: engineering notes

Notes for contributors and coding assistants. The application is a C# Avalonia desktop app on .NET 8, always on top, for tracking time against client accounts and preparing timesheets. It must run without installs or administrator rights. The earlier PowerShell/WinForms app (v2.32) was removed from the tree and lives in Git history.

## Layout

| Path | Role |

The `migration` folder name is historical and kept so updater and workflow paths still work. Renaming it is a separate change.

## Branches and releases

`main` is the Store release, `experimental` is everyday testing and `alpha` is for risky prototypes. Work on `experimental` or a `feature/...` branch from it, promote alpha to experimental and experimental to main by pull request, and never push straight to `main`. Builds show their channel beside the version, and only non-Store builds offer the sample-data demo. The updater serves experimental and alpha only, each with its own data, versions and backups. See `BRANCHES.md`.

## Behaviour to preserve

- **Credited totals.** Entries hold credited durations. Totals come from credited seconds, never from clock spans. Positioning credit never adds hours; "Add time" does.
- **Day clock.** The main clock is working plus overtime time, excluding Lunch, breaks and away. Stopping or switching an account does not reset it. Scheduled starts are automatic. A day off counts only tracked time. `SetShifts` drops manual starts the new hours make unnecessary. `ResumeAfterBreak` is stored with the running row. `BreakAccount.Name = "Break"` is reserved.
- **Exact decimal hours.** Exports apportion hundredths of an hour by largest remainder, first across account/day totals and then within each bucket, so every sum is exact. Running totals are provisional until saved.
- **Gaps.** Selected gaps are validated against the unrounded current gap before being moved to whole seconds, because durations use hundredths of a minute. Tidy day rechecks the whole selection before adding anything, as one undo step.
- **Switching accounts.** A block's length is kept to hundredths of a minute and its start to the second, so `TrackingEngine.ToggleAccount` starts the new block at the whole second after the old one's stored end when needed, and consecutive blocks never overlap. The timeline also treats blocks within two seconds as meeting, so older overlaps do not split the day into lanes. After a quick slip from one account to another and back (a block of three minutes or less, switched back within three minutes, `TrackingEngine.ContinuableBlocks`), `ContinuePrevious` drops the short block and reopens the earlier one so it carries on as one, with the slip's time. It is offered in the dashboard footer, the pill's list, the right-click menu and the recording block's menu, and not for blocks in a group. Pressing play on an account whose block the time now falls inside (one added or pasted ahead of time) carries that block on instead of starting a second one on top of it (`TrackingEngine.FutureBlockOf`, `ContinuedBlock`): it is reopened from its own start, stopping ends it where the recording stops, and it is skipped for a block in a group or one that would overlap other recorded time. A break is carried on the same way, so starting a break inside a break block already there reopens it.
- **Selecting and opening timeline blocks.** Clicking a block selects or deselects it (so two clicks make a pair to merge), and there is no double-click to edit, which could not be told apart from two clicks and once opened the wrong account. The Edit button in the bar under the workspace (`EditSelected`, called Inspect for a group, shown when exactly one block is selected, `TimerModel.EditSelection`), Enter, and the right-click menu open the editor. Double-clicking empty space still adds time.
- **Dragging to a neighbour.** A block's end is kept to the whole second and its length to hundredths of a minute, so `TimelineGestures` snaps an edge to the neighbour's start with `LastDeltaBefore`, which steps back a second at a time until the saved block really ends no later than it. This matters most for the block being recorded, whose start has a fraction of a second.
- **Undo.** Edits are stored as splices plus hashes in `edits` and `edit_changes`, so history stays small and survives restarts.

## Storage

`TimerDatabase` holds accounts, entries, groups, away, day_starts, running, edits, edit_changes and meta. It takes an exclusive lock, uses WAL and `user_version`, and makes daily backups. The schema is format 2 (a budget can be per day), and `TimerDatabase.Upgrades` holds the numbered steps that take an older file forward after a copy is saved; a step that rebuilds a table runs with foreign keys off and is checked with `foreign_key_check` before it is kept, and an older build refuses a newer file. Dispose every `SqliteCommand` or Windows keeps the file locked, which fails tests on CI. `TimerStore` rewrites `entries` when a snapshot changes. Notes, groups and `accountsSeeded` are blobs in `meta`. The settings JSON preserves unknown sections and is swapped in atomically with a `.bak`. Sessions checkpoint every 15 seconds and recovery stops at the last checkpoint. `TimerStore` refuses a folder holding the old `AccountTimer2.ps1` or launcher, and the old CSV files are deliberately never imported. Never auto-open another app's data folder. Never commit `migration-data`, `timer.db`, settings JSON or logs (`.gitignore` excludes them).

## Themes

Each theme is a `ThemeDefinition` (name, Light or Dark base, colour tokens, block style) and an Avalonia `ThemeVariant`. `ThemeTokens.Names` lists the tokens (Surface, Panel, Ink, Muted, Line, Hover, Selected, Live, Idle, Overtime, BudgetWarning, Break, Finish, Start, Accent, AccentInk, Clock, PillSurface, PillInk, PillBreak, PillOvertime, ShadowColor). `ThemeEngine.Register` writes brushes into `Application.Resources.ThemeDictionaries` in place so open windows repaint. Built-ins register in `App.Initialize`, user themes in the `TimerModel` constructor and on save. The pill is a capsule that wears its state: the normal theme when idle, the theme's pill colour while recording, its pill break colour on a break and its pill overtime colour in overtime (`ThemeDerivation.Variant`, registered as `Recording`, `Break` and `Overtime` variants, with break outranking overtime outranking recording). Text, lines and hovers inside it are mixed from the capsule colour and its text colour, and the colours that normally carry meaning (break, overtime, finish) become that text colour. Capsule colours that are too dull to carry text are brightened (`ThemeLibrary.Capsule`), and a dark theme's overtime colour is deepened. The pill is 516 by 82 and grows into a rounded card when opened. The whole pill is drawn at 85 per cent of that at most, and smaller on a narrow screen (below about 1500 device independent pixels) or a low Windows scale (100 per cent gives 70 per cent, 125 per cent or more gives 85 per cent), because a display with fewer pixels to the inch makes the same pill look bigger (`PillWindow.ScaleFor`, applied by `FitToScreen` through a layout transform). The size is worked out again whenever the pill is shown, when it is dragged onto another screen (`FitIfScreenChanged`, on position changes) and when Windows changes a screen's scale. A size chosen in Settings, Pill size (`TimerModel.PillScalePercent`, 50 to 120 per cent, saved as `pill=NN` or `pill=auto` in the appearance lines) overrides it and applies at once, even while the pill is hidden; with no screen to measure the size is left as it is. The window is always brought to the size the scale and state call for by `PillWindow.EnsureSize`, never only when the scale moves (that left a white card under the capsule when the scale was set before the window showed), and it is run after every scale change, when the window opens, when its real size is wrong, and a quarter of a second after the last move of a drag, because Windows ignores size changes during the drag and a pill dragged to another screen would otherwise keep its old window size. The default is System (`ThemeLibrary.Default`), which is Light or Dark by the computer's light or dark setting (`TimerModel.CurrentTheme` resolves it and re-resolves when Windows changes; the app always requests an explicit variant). Six built-ins ship: Light and Dark (the Time Deck palettes) and the studies Studio, After Hours, Botanical and Hawthorn (add more to `ThemeLibrary.BuiltIn` and every list picks them up). A study is set by hand from six colours (surface, panel, text, accent, break, overtime) plus the tracking green, and `ThemeLibrary.Themed` works out quiet text, lines, hovers and selection so each holds the contrast tests. They have no per-theme account palettes yet. `ThemeLibrary.Renamed` maps names that were renamed or removed (Time Deck, Sage, Ocean and so on) onto Light or Dark by their base. Only a missing theme setting defaults to `ThemeLibrary.Default`; a saved choice is kept. Tests require Ink on Surface and Panel at 7:1, Muted on Surface at 3.5:1 and AccentInk on Accent at 4.5:1 for every built-in, and Ink at 4.5:1 and Muted at 3:1 on the pill's state colours. Writing a theme (`ThemeEngine.Write`) replaces only the resources whose colour changed, because replacing one makes every control using it look again, and a preview (`TimerModel.PreviewTheme`, `ThemeEngine.RegisterPreview`) writes only the main variant, not the pill's tinted ones. The theme editor shows its first change at once and gathers the rest to at most one repaint every 70 ms, builds each colour picker only when it first opens (a `ColorSpectrum` wheel in ring shape, a `ColorSlider` bar for lightness and a hex box, from the `Avalonia.Controls.ColorPicker` package, whose styles are included in `App.axaml` because FluentTheme does not load them), and putting the saved look back after a preview re-registers just the theme that was edited. Built-ins are locked in the editor; the editor asks before discarding unsaved edits. Every timeline block has the same corner (`ReviewViews.BlockRadius`, 6, less only for a block too short to hold it). Timeline blocks are drawn by the theme's block rules (`ThemeDerivation.Block`, via `TimerModel.BlockLook`). The style is solid (the account colour), softened, or tinted (`BlockTint` is how much account colour the fill takes and `BlockEdge` how far the left edge moves towards the text colour), and every block has a strip down its left side. Light and Dark both tint their blocks. Charts use `TimerModel.ChartColour`, which is the account's own colour in dark themes because tinted fills sink into the dark surface. Clocks and big numbers use Bricolage Grotesque (SIL Open Font License, `Assets/Fonts`), bundled as three instances cut from the variable font, each its own family (`ClockFont`, `FiguresFont`, `ClockLightFont`, built in `App.Initialize` and used through the `clock`, `figures` and `clockLight` classes).

## UI conventions and pitfalls

- Pop-ups are dialogs, not windows. `Dialog` (in `Dialogs.cs`) is a `ContentControl` with a Title, Width and a `Close()`, shown by the dashboard's `DialogHost` (`DashboardWindow.Dialogs`) on a card over a dim scrim, with the dashboard blurred and unclickable behind it, like the getting started setup. They stack, and Escape or the cross closes the top one before it clears a selection. Every pop-up is one (`EntryDialog`, `TidyDialog`, `GroupDialog`, `ExportDialog`, `AccountsDialog`, `ShiftDialog` and `ThemesDialog`); only the pill and the dashboard are windows. The host draws the card's header (the dialog's Title on the left and the cross on the right) above the dialog's own content, so a dialog does not repeat its title and a scroll bar never runs under the cross. Buttons inside dialogs use `Ui.DialogButton`, which gives the dashboard's quiet outlined look (`toolButton quiet`) and an accent outline on the main action (`mainAction`, for Save, Export and the like). A dialog can refuse to close through its `Closing` event, which is how the theme editor asks about unsaved edits. Their height follows their content up to the window. In tests, `TestDialogs.Open` shows a dialog over a dashboard. A hidden dashboard shows no dialog, so the pill's Name and budget menu item asks the model (`TimerModel.OpenAccounts`) and the dashboard comes up first (`DashboardWindow.Reveal`).
- Headings in pop-ups, the settings page and the dashboard use `Ui.Heading`, the `clock` display face, and every button in a pop-up or on the settings page is a `Ui.DialogButton`. Tooltips, notes, refused-edit messages and explainer lines are kept to a short phrase. `WindowCoordinator.KeepInFront` puts a window back at the front of the topmost band when it loses focus and every five seconds while it is not active, because snapping another window over the timer could leave it hidden.
- Messages float. `MessageBar` sits over the lowest part of the workspace, above the buttons, so a note, a refused edit or a failed save never moves the buttons. It has its own raised look (`messageBar`, panel colour, accent outline and a shadow) so it shows against any block. Its style is written `:is(Border).messageBar`, because a plain `Border.x` selector skips a subclass such as `MessageBar`, which once left it with no background. Notes and refused edits fade after 15 seconds (`TimerModel.MessageLifetime`), a failed save stays until a save works, and the cross hides it until it changes. The Continue earlier block button lives in the same bar.
- A selected block or entry is shown by its left edge in the theme's accent colour, a little wider (`selectedEdge`), with no outline. The `mergeSelected` class stays on the block so it can be found.
- Settings are a page, not a menu. `SettingsView` fills the dashboard workspace (rail gear, button name `Settings`), is built once when opened and not rebuilt on model changes, and reuses `ShiftEditor`, which is also the working hours window. The right-click menu (`Ui.SettingsMenu`) is only Continue earlier block, the version, Test overtime (demo) and Collapse to tray (`TimerModel.RequestHide`, which the coordinator turns into hiding to the tray, or minimising when there is none; Decimal hours lives on the settings page), and the version and Test overtime show only when developer features are unlocked (`TimerModel.DeveloperUnlocked`, saved as `developer=on`; a demo always counts as unlocked; Store builds never unlock, and `StoreBuildTests` proves it by setting `BuildInfo.DeveloperFeaturesOverride` to false, since the tests are built without the Store flag). Ten quick clicks on the About tile in settings unlock them (`SettingsView.UnlockClicks`), and the Development section there (sample-data demo, and a switch to hide them again) appears only when unlocked. In the demo that section is always shown with the switch fixed on and a note instead of the demo button.
- A new database starts with the getting started setup (`OnboardingView`, four steps: accounts and optional budgets, working hours, hours format and week start, then a page of things to know). `StoreSettings.SetupDone` is saved as `setup=done` or `setup=pending` in the appearance lines. A database with neither line counts as done, unless it was just created, so existing users never see it. `DashboardWindow.UpdateOnboarding` lays it over the dashboard, which is blurred and not clickable while it shows, and `App` opens the dashboard first when the setup is pending. Each step applies on Next, and Skip setup or Esc finishes it, leaving the starting accounts alone. Controls on a step must be detached from their old parent when a step is rebuilt (`Detach`). Settings has Run setup again (`TimerModel.RestartSetup`). Tests that use a real new database should call `CompleteSetup` or the overlay will catch their clicks.
- Accounts can be deleted from Accounts and budgets (the bin on each row marks it, and Save does it). `TimerModel.SetAccounts` takes a `deleted` list, and `LedgerEditor.DeleteAccount` removes the account's entries, notes and groups and clears the Undo history, like a rename. An account with recorded time asks for confirmation in the window first (`DeleteConfirm`), a `before-delete` backup is saved, and a running account is stopped. Removing an account from the list any other way is still refused, so it has to be hidden instead.
- Every window calls `WindowChrome.Attach(this)`, which gives it the app icon and, on Windows 11, a title bar in the theme's colours that follows theme changes and previews (`ThemeEngine.Applied`). Older Windows keeps its normal title bar.
- There is no Adjust time feature. Databases made while it existed are cleaned when they open: `TimerStore` leaves `adjustment` rows out, keeps a `before-removing-adjustments` backup, drops their notes and clears the undo history (`AdjustmentsRemoved` drives a notice). The schema's `adjustment` kind is left in place, since SQLite cannot drop a CHECK value cheaply.
- The taskbar button is on by default and `TaskbarButton` can be switched off only once the tray exists (`TrayAvailable`).
- Use the helpers in `Controls.cs` (`Ui.Grid`, `Ui.Put`, `Ui.Button`, `Ui.IconButton`, `Ui.Text`). Style through classes in `App.axaml` and `DynamicResource` theme tokens rather than hard-coded colours.
- `Ui.Visible` lifts very dark account colours so dots and blocks stay visible on dark themes; `Ui.InkOn` picks text for a block.
- Drag handlers mark presses as handled, so they must call `Ui.CloseMenus` first or an open right-click menu stays open.
- Tooltips take their colours from the theme (`ToolTipBackground`, `ToolTipForeground` and `ToolTipBorderBrush` are written from Surface, Ink and Line for every theme and pill state in `ThemeEngine.Write`), so they never show dark text on a dark tooltip. In the pill, the account name and the second line are `AutoScrollText` inside a `NameRow`, which slide to their end and back when too long, and the chevron stays beside the name. The older `MarqueeText` is the hover scroll in account lists.
- Tooltips can be switched off in settings (`TimerModel.Tooltips`, saved as `tooltips=off` in the appearance lines). `Ui.ApplyTooltips` adds one class handler that cancels `ToolTip.ToolTipOpeningEvent`, which is a direct event, so a handler on the window would never see it. The Live token is green (tracking), and the recording pill lifts it to read on its dark surface (`ThemeDerivation.Variant`). Add time, Undo and Merge share the bar under the workspace with the zoom controls.
- The week views (`ReviewViews.OverviewSection`, `HoursSection`, `EntriesSection`) sit on `Card` tiles (the `dayCard` class). Keep the button names `WeekEntry<n>`, `WeekReviewEntry`, `CopyHours`, `ExportWeek` and `Ungroup<id>`, and the `entryRow` class for entry rows. Figures use the `figures` class.
- The entry window (`EntryWindow`) has start, end and length boxes that follow each other (the length is minutes, H:MM or H:MM:SS). A longer end on the same start and account asks whether to move the later blocks (`LedgerEditor.PlanExtend` and `ExtendEnd`) or to allow the overlap (`LedgerEditor.Edit` with `allowOverlap`, never onto the block being recorded). Overlaps count the shared hours twice, as chosen. A tick box in the question, or the switch in settings, keeps the choice (`TimerModel.MoveLaterAlways`, saved as `shove=always` in the appearance lines) so later blocks move without asking.
- Copy and paste live in `TimerModel` (`CopyBlocks`, `PasteBlocks`, `DefaultPasteTime`) and `LedgerEditor.Paste`. Copied blocks are kept inside the app, not on the system clipboard, so they carry their credited minutes exactly. A paste checks every block before adding any and is one undo step. Pasting adds credited time, like Add time.
- The timeline (`ReviewViews.Timeline`) is a canvas with a spine at x 58, ticks, hour guides and a now marker for today (a 30 second `DispatcherTimer` while attached). Cards start at x 80. Tag the canvas children (`Tick`, `HourGuide`, `NowLine`) when `Resize` must find them, since the spine and ticks also use the `rule` class. Zoom lives in a bar under the timeline (`TimelineControls`, with the `TimelineZoom` slider on a logarithmic scale via `TimerModel.TimelineZoomFraction` and `ScaleAt`).
- `ThemeEngine` also writes the Fluent slider and tick box resources from the theme's Accent, AccentInk and Line, so those controls follow the theme instead of the computer's accent colour. Start day uses its own `Start` token (green), not `Live`.
- The dashboard is a fixed 1080 by 680 (`DashboardWindow.DashboardWidth` and `DashboardHeight`). The way back to the pill is the first button on the icon rail and Close timer (`QuitTimer`, which turns red and swells a little under the pointer) is the last, below settings. The Day elapsed card is now headed Working time, since the clock leaves out breaks. An icon rail picks the view (the buttons keep the names `TimelineTab`, `WeekOverviewTab`, `WeekHoursTab` and `WeekEntriesTab`, with their words as the tooltip), the left column is the Day elapsed card over `AccountList` in `bars` mode (`BudgetBar` with a pace tick, plain `AccountIndicator` circle with `Ring` off), and the clock is a `ClockText` coloured through `SetState`.
- Pill and dashboard are separate windows sharing one model. Do not resize a visible window to change views. The dashboard is `Topmost`.
- Headless tests: `DispatcherTimer` and animations do not tick, so test state not frames. `TextBox.TextChanged` does not fire, so listen to `PropertyChanged` on `TextBox.TextProperty`.
- Fault-injection helper `StorageFaults` (in `EditingTests.cs`) uses triggers to make saves fail.
- Keep the C# for `Timer.Core` and `Timer.Storage` free of UI types.

## Keeping builds few

Each merge into `experimental` or `alpha` builds and stores a Windows ZIP (kept 14 days), and a pull request run adds tests on three systems. The owner tests only every few versions, so batch work: keep related changes on one `feature/...` branch, open one pull request for the lot, and sync `experimental` only for a candidate. Before opening a pull request for a small change, ask whether it can wait for the next one. Rendered previews upload only when a test fails or a run is started by hand.

## Checking changes

Run `dotnet test migration/tests/Timer.Desktop.Tests -c Release`. CI runs it on Windows, Linux and macOS and publishes a self-contained Windows build; check the run before saying tests pass. The user tests visuals on Windows and reports back with screenshots.

## Conventions

- Record changes in `CHANGELOG.md`, newest first, each row linked to its commit.
- Comments in plain English explaining why.
- Interface text and documentation use British spelling, no em dashes, no mid-sentence colons, no arrows or unusual characters, plain human wording. Say "client accounts".
- Test with synthetic data only.
