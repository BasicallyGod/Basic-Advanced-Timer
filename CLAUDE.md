# Basic’s Advanced Timer: engineering notes

Notes for contributors and coding assistants. The application is a C# Avalonia desktop app on .NET 8, always on top, for tracking time against client accounts and preparing timesheets. It must run without installs or administrator rights. The earlier PowerShell/WinForms app (v2.32) was removed from the tree and lives in Git history.

## Branches and releases

`main` is the Store release, `experimental` is everyday testing and `alpha` is for risky prototypes. Work on `experimental` or a `feature/...` branch from it, promote alpha to experimental and experimental to main by pull request, and never push straight to `main`. Builds show their channel beside the version, and only non-Store builds offer the sample-data demo. The updater serves experimental and alpha only, each with its own data, versions and backups. See `BRANCHES.md`.

## Behaviour to preserve

- **Working time and allocation.** Reports show Working time as Allocated (time on accounts) plus Unallocated (working clock time not on any account, never below zero), with Breaks separate and not counted. The running entry's elapsed time is included (`TrackingEngine.ActiveElapsedOn`). Budget figures for an earlier week use that week's own period (`TimerModel.BudgetReference`, `BudgetUsedAt`, `BudgetPeriodNameAt`, the Thursday rule), never "this month". Hiding an account (In tracker) only removes it from the tracker list. Its time stays in `ReviewAccounts` and every report. Scroll views that end above fixed controls use `Ui.WithMoreBelow`, which draws a one pixel line in the theme's Line colour along the edge with more content past it, below and, once scrolled, above (a fade or shadow looked muddy on light themes).
- **Colour roles.** Green (`Live`) means tracking only, the accent means selection, focus and the main action (a blue in Light and Dark, kept clear of red, green and orange), amber means a break, `BudgetWarning` means a budget at 80 per cent and red (`Overtime`) means overtime or a spent budget. A budget bar with room left is neutral (`Muted`), the setup's current step dot is the accent, and the idle pill dot is `Idle`.
- **Duration format.** Every duration reads as HH:MM (`TimerModel.Format`, `FormatShort` and `FormatCompact` all give 01:30), and as decimal hours when that is chosen. Do not add a new way of writing one. The one exception is the Deadline tile's countdown, which reads as 26h 45m so that it cannot be taken for a time of day.
- **Credited totals.** Entries hold credited durations. Totals come from credited seconds, never from clock spans. Positioning credit never adds hours; "Add time" does.
- **Day clock.** The main clock is working plus overtime time, excluding Lunch, breaks and away. Stopping or switching an account does not reset it. Scheduled starts are automatic. A day off counts only tracked time. An overnight shift is one whose end is earlier than its start (22:00 to 06:00; only an equal end is refused): it belongs to the day it starts and ends on the next date (`WorkSchedule.PlanOf`, `IsOvernight`, `Tail`). The working day a moment belongs to is `TrackingEngine.ShiftKey` (`CurrentKey`): its own date, except until six hours after an overnight shift ends (`OvertimeTail`) or the next shift starts, when it is the shift's date, so the clock, Finish day and Start day carry on across midnight and an open finish stops at the next shift's start (`AwayBoundary`). The clock, overtime, Today figures and the Day tile use `ShiftTotals(key)` and `ShiftWindow(key)` (the whole shift across midnight, with a day shift after a night shift leaving out the night shift's tail); reports, the timeline and the week views stay by calendar day through `Totals(day)`, which for a day an overnight shift touches holds the tail of last night's shift and the start of tonight's. Day shifts take the older paths unchanged (`DayOnlyTotals`). `SetShifts` drops manual starts the new hours make unnecessary. `ResumeAfterBreak` is stored with the running row. `BreakAccount.Name = "Break"` is reserved.
- **Exact decimal hours.** Exports apportion hundredths of an hour by largest remainder, first across account/day totals and then within each bucket, so every sum is exact. Running totals are provisional until saved.
- **Gaps.** Selected gaps are validated against the unrounded current gap before being moved to whole seconds, because durations use hundredths of a minute. Tidy day rechecks the whole selection before adding anything, as one undo step.
- **Switching accounts.** A block's length is kept to hundredths of a minute and its start to the second, so `TrackingEngine.ToggleAccount` starts the new block at the whole second after the old one's stored end when needed, and consecutive blocks never overlap. The timeline also treats blocks within two seconds as meeting, so older overlaps do not split the day into lanes. After a quick slip from one account to another and back (a block of three minutes or less, switched back within three minutes, `TrackingEngine.ContinuableBlocks`), `ContinuePrevious` drops the short block and reopens the earlier one so it carries on as one, with the slip's time. It is offered in the dashboard footer, the pill's list, the right-click menu and the recording block's menu, and not for blocks in a group. Pressing play on an account whose block the time now falls inside (one added or pasted ahead of time) carries that block on instead of starting a second one on top of it (`TrackingEngine.FutureBlockOf`, `ContinuedBlock`): it is reopened from its own start, stopping ends it where the recording stops, and it is skipped for a block in a group or one that would overlap other recorded time. A break is carried on the same way, so starting a break inside a break block already there reopens it.
- **Selecting and opening timeline blocks.** Clicking a block selects or deselects it (so two clicks make a pair to merge), and there is no double-click to edit, which could not be told apart from two clicks and once opened the wrong account. The Edit button in the bar under the workspace (`EditSelected`, called Inspect for a group, shown when exactly one block is selected, `TimerModel.EditSelection`), Enter, and the right-click menu open the editor. Double-clicking empty space still adds time.
- **Dragging to a neighbour.** A block's end is kept to the whole second and its length to hundredths of a minute, so `TimelineGestures` snaps an edge to the neighbour's start with `LastDeltaBefore`, which steps back a second at a time until the saved block really ends no later than it. This matters most for the block being recorded, whose start has a fraction of a second.
- **Undo.** Edits are stored as splices plus hashes in `edits` and `edit_changes`, so history stays small and survives restarts.

## Storage

`StoreSettings` holds only the settings every app shares. Appearance lines and JSON sections the library does not own travel in `StoreSettings.Extras` (`SettingsExtras`) and are saved back untouched, so an app keeps its own settings without the shared record growing; `AppPrefs` (Timer.Desk) reads and writes this app's lines (`dash=`, `desk-*`, `motion=`, `pillstyle=`, `capturekey=`, `floattop=`) and sections (`deskTrinkets`, `deskLayouts`, `deskFloating`) and leaves any other app's alone. This is the boundary for sharing Timer.Core and Timer.Storage with another app.

`TimerDatabase` holds accounts, entries, groups, away, day_starts, running, edits, edit_changes and meta. It takes an exclusive lock, uses WAL and `user_version`, and makes daily backups. The schema is format 3 (format 2 allowed a budget per day, format 3 adds `day_notes`, notes on a day with an optional time, kept outside the undo history and edited one statement at a time through `TimerStore`'s `AddDayNote`, `UpdateDayNote` and `DeleteDayNote`), and `TimerDatabase.Upgrades` holds the numbered steps that take an older file forward after a copy is saved; a step that rebuilds a table runs with foreign keys off and is checked with `foreign_key_check` before it is kept, and an older build refuses a newer file. Dispose every `SqliteCommand` or Windows keeps the file locked, which fails tests on CI. `TimerStore` rewrites `entries` when a snapshot changes. Notes, groups and `accountsSeeded` are blobs in `meta`. The settings JSON preserves unknown sections and is swapped in atomically with a `.bak`. Sessions checkpoint every 15 seconds and recovery stops at the last checkpoint. `TimerStore` refuses a folder holding the old `AccountTimer2.ps1` or launcher, and the old CSV files are deliberately never imported. Never auto-open another app's data folder. Never commit `migration-data`, `timer.db`, settings JSON or logs (`.gitignore` excludes them).

## Themes

Each theme is a `ThemeDefinition` (name, Light or Dark base, colour tokens, block style) and an Avalonia `ThemeVariant`. `ThemeTokens.Names` lists the tokens (Surface, Panel, Ink, Muted, Line, Hover, Selected, Live, Idle, Overtime, BudgetWarning, Break, Finish, Start, Accent, AccentInk, Clock, PillSurface, PillInk, PillBreak, PillOvertime, ShadowColor). `ThemeEngine.Register` writes brushes into `Application.Resources.ThemeDictionaries` in place so open windows repaint. Built-ins register in `App.Initialize`, user themes in the `TimerModel` constructor and on save. The pill is a rounded card (24 pixel corner, with the account's colour in a rounded badge, `PillBadge`) that wears its state: the normal theme when idle, the theme's pill colour while recording, its pill break colour on a break and its pill overtime colour in overtime (`ThemeDerivation.Variant`, registered as `Recording`, `Break` and `Overtime` variants, with break outranking overtime outranking recording). Text, lines and hovers inside it are mixed from the capsule colour and its text colour, and the colours that normally carry meaning (break, overtime, finish) become that text colour. Capsule colours that are too dull to carry text are brightened (`ThemeLibrary.Capsule`), and a dark theme's overtime colour is deepened. The pill is 82 high and grows taller when opened, keeping its corner. Its width and arrangement come from the chosen layout (`PillLayouts`, `TimerModel.PillStyle`, saved as `pillstyle=full|compact|minimal`, picked in Settings from three small pictures): Full is 516 wide with the clock first, the account, today's time and the day's progress line; Compact is 520 wide with the account first, then the clock, and no progress line; Minimal is 360 wide with a badge of the account's initials (the amber dot on a break), the clock and pause, and no break button (Start break is on the right-click menu). `PillWindow.ApplyLayout` rearranges the same controls for each, and an open list is at least 420 wide. An open pill is at most three fifths of the screen's height (`PillWindow.OpenShareOfScreen`): the account list scrolls inside its own box (`PillAccountScroll`, `ListMaxHeight`) so Finish day stays in view. With nothing running the pill says what it waits for: the chosen account with Ready to track, or Ready to track with Select an account when none is chosen. The whole pill is drawn at 85 per cent of that at most, and smaller on a narrow screen (below about 1500 device independent pixels) or a low Windows scale (100 per cent gives 70 per cent, 125 per cent or more gives 85 per cent), because a display with fewer pixels to the inch makes the same pill look bigger (`PillWindow.ScaleFor`, applied by `FitToScreen` through a layout transform). The size is worked out again whenever the pill is shown, when it is dragged onto another screen (`FitIfScreenChanged`, on position changes) and when Windows changes a screen's scale. A size chosen in Settings, Pill size (`TimerModel.PillScalePercent`, 50 to 120 per cent, saved as `pill=NN` or `pill=auto` in the appearance lines) overrides it and applies at once, even while the pill is hidden; with no screen to measure the size is left as it is. The window is always brought to the size the scale and state call for by `PillWindow.EnsureSize`, never only when the scale moves (that left a white card under the capsule when the scale was set before the window showed), and it is run after every scale change, when the window opens, when its real size is wrong, and a quarter of a second after the last move of a drag, because Windows ignores size changes during the drag and a pill dragged to another screen would otherwise keep its old window size. The default is System (`ThemeLibrary.Default`), which is Light or Dark by the computer's light or dark setting (`TimerModel.CurrentTheme` resolves it and re-resolves when Windows changes; the app always requests an explicit variant). Five built-ins ship: Light (the former Studio palette, worked out by `ThemeLibrary.Themed`) and Dark, and the studies After Hours, Botanical and Hawthorn (add more to `ThemeLibrary.BuiltIn` and every list picks them up). A study is set by hand from six colours (surface, panel, text, accent, break, overtime) plus the tracking green, and `ThemeLibrary.Themed` works out quiet text, lines, hovers and selection so each holds the contrast tests. They have no per-theme account palettes yet. `ThemeLibrary.Renamed` maps names that were renamed or removed (Studio, Time Deck, Sage, Ocean and so on) onto Light or Dark by their base. Only a missing theme setting defaults to `ThemeLibrary.Default`; a saved choice is kept. Tests require Ink on Surface and Panel at 7:1, Muted on Surface at 3.5:1 and AccentInk on Accent at 4.5:1 for every built-in, and Ink at 4.5:1 and Muted at 3:1 on the pill's state colours. Writing a theme (`ThemeEngine.Write`) replaces only the resources whose colour changed, because replacing one makes every control using it look again, and a preview (`TimerModel.PreviewTheme`, `ThemeEngine.RegisterPreview`) writes only the main variant, not the pill's tinted ones. The theme editor shows its first change at once and gathers the rest to at most one repaint every 70 ms, builds each colour picker only when it first opens (a `ColorSpectrum` wheel in ring shape, a `ColorSlider` bar for lightness and a hex box, from the `Avalonia.Controls.ColorPicker` package, whose styles are included in `App.axaml` because FluentTheme does not load them), and putting the saved look back after a preview re-registers just the theme that was edited. Built-ins are locked in the editor; the editor asks before discarding unsaved edits. Every timeline block has the same corner (`ReviewViews.BlockRadius`, 6, less only for a block too short to hold it). Timeline blocks are drawn by the theme's block rules (`ThemeDerivation.Block`, via `TimerModel.BlockLook`). The style is solid (the account colour), softened, or tinted (`BlockTint` is how much account colour the fill takes and `BlockEdge` how far the left edge moves towards the text colour), and every block has a strip down its left side. Light and Dark both tint their blocks. Charts use `TimerModel.ChartColour`, which is the account's own colour in dark themes because tinted fills sink into the dark surface. Clocks and big numbers use Bricolage Grotesque (SIL Open Font License, `Assets/Fonts`), bundled as three instances cut from the variable font, each its own family (`ClockFont`, `FiguresFont`, `ClockLightFont`, built in `App.Initialize` and used through the `clock`, `figures` and `clockLight` classes).

## UI conventions and pitfalls

- Pop-ups are dialogs, not windows. `Dialog` (in `Dialogs.cs`) is a `ContentControl` with a Title, Width and a `Close()`, shown by the dashboard's `DialogHost` (`DashboardWindow.Dialogs`) on a card over a dim scrim, with the dashboard blurred and unclickable behind it, like the getting started setup. They stack, and Escape or the cross closes the top one before it clears a selection. Every pop-up is one (`EntryDialog`, `TidyDialog`, `GroupDialog`, `ExportDialog`, `AccountsDialog`, `ShiftDialog` and `ThemesDialog`); only the pill and the dashboard are windows. The host draws the card's header (the dialog's Title on the left and the cross on the right) above the dialog's own content, so a dialog does not repeat its title and a scroll bar never runs under the cross. Buttons inside dialogs use `Ui.DialogButton`, which gives the dashboard's quiet outlined look (`toolButton quiet`) and an accent outline on the main action (`mainAction`, for Save, Export and the like). A dialog can refuse to close through its `Closing` event, which is how the theme editor asks about unsaved edits. Their height follows their content up to the window. In tests, `TestDialogs.Open` shows a dialog over a dashboard. A hidden dashboard shows no dialog, so the pill's Name and budget menu item asks the model (`TimerModel.OpenAccounts`) and the dashboard comes up first (`DashboardWindow.Reveal`).
- Headings in pop-ups, the settings page and the dashboard use `Ui.Heading`, the `clock` display face, and every button in a pop-up or on the settings page is a `Ui.DialogButton`. Tooltips, notes, refused-edit messages and explainer lines are kept to a short phrase. `WindowCoordinator.KeepInFront` puts a window back at the front of the topmost band when it loses focus and every five seconds while it is not active, because snapping another window over the timer could leave it hidden. Each window can be taken off the topmost band in settings (`TimerModel.PillOnTop` and `DashboardOnTop`, saved as `pilltop=off` and `dashtop=off`), and then `KeepInFront` and `BringToFront` leave it alone. It also does nothing while a topmost window of another app has the focus (`ZOrder.ShouldReassert`, `ZOrder.ForegroundIsTopmost`), or it would jump on top of the screenshot tool's overlay. The cross on the `MessageBar` puts away both the line and the continue offer (until the offer's words change).
- Messages float. `MessageBar` sits centred over the lowest part of the workspace, above the buttons, so a note, a refused edit or a failed save never moves the buttons. It has its own raised look (`messageBar`, panel colour, accent outline and a shadow) so it shows against any block. Its style is written `:is(Border).messageBar`, because a plain `Border.x` selector skips a subclass such as `MessageBar`, which once left it with no background. Notes and refused edits fade after 15 seconds (`TimerModel.MessageLifetime`), a failed save stays until a save works, and the cross hides it until it changes. The Continue earlier block button lives in the same bar. Selection feedback is not a message. `SelectionStrip` is a quiet strip in the layout just above the Add time, Undo and Merge buttons (panel colour, a hairline on top, nothing in the accent colour). It shows the count (`TimerModel.SelectionCountText`), one short note naming the specific merge problem (`SelectionNote`) and a Clear selection text button. The full merge rule lives in the Merge tooltip (`MergeHint`).
- A selected block or entry is shown by its left edge in the theme's accent colour, a little wider (`selectedEdge`), with no outline. The `mergeSelected` class stays on the block so it can be found.
- Settings are a dialog, not a page (`SettingsDialog`, 940 by 640, opened by the rail gear, which toggles it, and by Settings… on the pill's menu through `TimerModel.RequestSettings`, which brings the dashboard up first). `SettingsView` is a rail of categories on the left (`SettingsCategory_<key>`: General, Appearance, Pill, Desk, Working hours, Accounts and budgets, About, and Development only once unlocked) and one pane on the right, so the card keeps its size and a long pane scrolls inside it (`SettingsPage` is the scroll viewer). Every pane is built once and swapped in, not rebuilt on model changes, and listens to the model through `syncs`; tests choose a pane with `OpenCategory`. Working hours reuses `ShiftEditor` laid out as a row of seven days (`week: true`), and Accounts and budgets is the `AccountsDialog` body edited in place (`TakeBody`, built again after Save or Revert). While a dialog is open the window's top band does not pick the window up by its text (`Dialogs.Any` in the drag handler). Run setup again closes the dialog first, since the setup lays itself over the dashboard. The pill's right-click menu (`Ui.SettingsMenu(model, pill: true)`) starts with quick actions, Open dashboard (Open Desk when the desk is on, `TimerModel.RequestDashboard`), Quick switch account (a submenu of the accounts, the running one ticked), Start or End break, Add note (`TimerModel.RequestQuickCapture`, the small Quick capture box below, with no dashboard; the Add a note and Add a deadline buttons in tiles still use `TimerModel.RequestNote` and the dashboard's `NoteDialog`) and Pin to screen (the pill's always on top switch), Settings… (`SettingsMenu`), then the items below. Close timer is deliberately not on it. The dashboard's menu stays as described next: only Continue earlier block, the version, Test overtime (demo) and Collapse to tray (`TimerModel.RequestHide`, which the coordinator turns into hiding to the tray, or minimising when there is none; Decimal hours lives on the settings page), and the version and Test overtime show only when developer features are unlocked (`TimerModel.DeveloperUnlocked`, saved as `developer=on`; a demo always counts as unlocked; Store builds never unlock, and `StoreBuildTests` proves it by setting `BuildInfo.DeveloperFeaturesOverride` to false, since the tests are built without the Store flag). Ten quick clicks on the About tile in settings unlock them (`SettingsView.UnlockClicks`), and the Development section there (sample-data demo, and a switch to hide them again) appears only when unlocked. In the demo that section is always shown with the switch fixed on and a note instead of the demo button.
- Quick capture (`QuickCaptureWindow`, `QuickCapture.cs`) is a small borderless always-on-top box for a note from anywhere, opened by the pill menu's Add note or a shortcut (`TimerModel.QuickCaptureRequested`, handled by `WindowCoordinator.ShowQuickCapture`, one at a time). It takes the Notes shorthand, shows how the words were read (`QuickCaptureWindow.Describe`) and saves through `AddDayNote` on today (or the day it names), so it adds no storage of its own; Enter saves, Escape or clicking away closes. The shortcut (`HotkeySpec`, `Timer.Core/Hotkey.cs`: Ctrl, Alt or Win plus a letter, digit or F1 to F12, written Ctrl+Alt+N) is set by pressing it in Settings, General (`CaptureShortcut`, `CaptureShortcutClear`, `CaptureOpen`), saved as `capturekey=` (empty when none, off by default), and registered on Windows only by `GlobalHotkey` on the first timer window with a handle (a shortcut another app holds gives a notice, and nothing is registered on other systems).
- Floating widgets (`FloatingWidgetWindow`, `Timer.Core/FloatingWidgets.cs`): any desk tile can be lifted out of the desk by the Float button in its hover buttons (`TileFloat_<id>`, `TimerModel.FloatWidget`) into a borderless window of its own, at most three at a time (`FloatingWidgets.Max`; a fourth is refused with a notice), besides the pill. The window hosts a single-tile `DeskView` (`new DeskView(model, null, only: id)`), so it is the desk's own tile code, showing the same version of itself for its size in cells (`SetCells`, `VariantFor`), with a Dock button (`TileDock_<id>`, `TimerModel.DockWidget`) instead of the open, open-in-place and put-away ones; it is carried by its header (`BeginMoveDrag`), resized in whole cells from its corner grip (`DeskView.CellsChanged`, window size from `DeskView.PixelsFor` plus the shadow margin), and has the desk's surface under it (`surface` underlay) because a tile's colour is a wash and would otherwise show what is behind the window. On the desk the tile keeps its cells and shows a Floating on screen placeholder with a Dock button (`TileFloating_<id>`, `TileDockHere_<id>`). `WindowCoordinator.SyncFloating` opens and closes the windows when `TimerModel.FloatingChanged` fires and at start; they stay up when the dashboard is hidden to the tray, and are retired (not docked) when the app closes so they come back next time, while closing one any other way docks it. State is the JSON section `deskFloating` (id, screen position, size in cells, `TimerModel.Floating`, `MoveFloating` and `ResizeFloating` debounce the position by 400 ms); a window saved off every screen is brought back (`KeepOnAScreen`). They are on top of other windows unless switched off in Settings, Desk (`TimerModel.FloatOnTop`, saved as `floattop=off`). Hide floating widgets (the pill menu's `FloatingMenu` and the tray menu, only while something floats; `TimerModel.SetFloatingHidden`, this session only) tucks the windows away without docking them, and floating or docking brings them back.
- Visibility is tested, not just colours. `VisibilityTests` (with `VisibilityAudit`) opens the desk (arranging, with a floating tile), every tile at its smallest, usual and largest sizes while idle, tracking, on a break and in overtime, the Timeline and Timesheet pages, every Settings pane, the main dialogs, the pill in each layout and state, the pill and dashboard menus and Quick capture, in Light and in Dark, and checks that every piece of text, text box and icon holds 3 to 1 against what it sits on (the backgrounds behind it blended over the surface, with the colour transitions taken off, since nothing ticks headless); a new screen or state belongs in that list. Text in a status colour uses the derived `LiveInk`, `BreakInk` and `OvertimeInk` resources (`ThemeEngine.StatusInk`, the colour moved towards the text colour until it holds 4.5 to 1 on a surface tinted with it) through the `live`, `break` and `overtime` text classes, not the `Live`, `Break` and `Overtime` tokens, which stay for dots, bars and fills. Account-coloured tag text uses `TagColours.Text`, which reads the theme in use, not the control's resources, because the tag is built before it is in a window. The hint in an empty text box is a lighter mix of the text colour written as `TextControlPlaceholderForeground`, and `App.Initialize` takes the template's half-strength fade off (`PART_Watermark`).
- A new database starts with the getting started setup (`OnboardingView`, four steps: accounts and optional budgets, working hours, hours format and week start, then a page of things to know). `StoreSettings.SetupDone` is saved as `setup=done` or `setup=pending` in the appearance lines. A database with neither line counts as done, unless it was just created, so existing users never see it. `DashboardWindow.UpdateOnboarding` lays it over the dashboard, which is blurred and not clickable while it shows, and `App` opens the dashboard first when the setup is pending. Each step applies on Next, and Skip setup or Esc finishes it, leaving the starting accounts alone. Controls on a step must be detached from their old parent when a step is rebuilt (`Detach`). Settings has Run setup again (`TimerModel.RestartSetup`). Tests that use a real new database should call `CompleteSetup` or the overlay will catch their clicks.
- Accounts can be deleted from Accounts and budgets (the bin on each row marks it, and Save does it). `TimerModel.SetAccounts` takes a `deleted` list, and `LedgerEditor.DeleteAccount` removes the account's entries, notes and groups and clears the Undo history, like a rename. An account with recorded time asks for confirmation in the window first (`DeleteConfirm`), a `before-delete` backup is saved, and a running account is stopped. Removing an account from the list any other way is still refused, so it has to be hidden instead.
- Every window calls `WindowChrome.Attach(this)`, which gives it the app icon and, on Windows 11, a title bar in the theme's colours that follows theme changes and previews (`ThemeEngine.Applied`). Older Windows keeps its normal title bar.
- There is no Adjust time feature. Databases made while it existed are cleaned when they open: `TimerStore` leaves `adjustment` rows out, keeps a `before-removing-adjustments` backup, drops their notes and clears the undo history (`AdjustmentsRemoved` drives a notice). The schema's `adjustment` kind is left in place, since SQLite cannot drop a CHECK value cheaply.
- The taskbar button is on by default and `TaskbarButton` can be switched off only once the tray exists (`TrayAvailable`).
- Use the helpers in `Controls.cs` (`Ui.Grid`, `Ui.Put`, `Ui.Button`, `Ui.IconButton`, `Ui.Text`). Style through classes in `App.axaml` and `DynamicResource` theme tokens rather than hard-coded colours.
- `Ui.Visible` lifts very dark account colours so dots and blocks stay visible on dark themes; `Ui.InkOn` picks text for a block.
- Controls that draw themselves with `TryFindResource` (`IconGlyph`, `Chevron`, `PauseGlyph`, `BreakGlyph`, `AccountIndicator`, `BudgetBar`) must call `InvalidateVisual` when `ActualThemeVariant` changes, because the pill changes variant with its state and a stale brush can be unreadable. Tray menu items (`TrayController`) need their words set at construction, not only on the menu's Opening event.
- Slider colours come from `ThemeEngine.SliderColours` (an empty track that holds 3 to 1 on Surface and Panel, and a fill and thumb in the accent unless it is too faint), not from the theme's Line, which is only a hairline. Sliders in a built-in theme's editor are disabled, so the `...Disabled` slider resources are written too (`ThemeEngine.DisabledSliderColours`). ## Keeping builds few

Each merge into `experimental` or `alpha` builds and stores a Windows ZIP (kept 14 days), and a pull request run adds tests on Windows. The owner tests only every few versions, so batch work: keep related changes on one `feature/...` branch, open one pull request for the lot, and sync `experimental` only for a candidate. Before opening a pull request for a small change, ask whether it can wait for the next one. Rendered previews upload only when a test fails or a run is started by hand.

## Checking changes

Run `dotnet test migration/tests/Timer.Desktop.Tests -c Release`. CI runs it on Windows only and publishes a self-contained Windows build; check the run before saying tests pass. The user tests visuals on Windows and reports back with screenshots.

## Conventions

- Record changes in `CHANGELOG.md`, newest first, each row linked to its commit.
- Comments in plain English explaining why.
- Test with synthetic data only.
